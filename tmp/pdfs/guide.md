# 01. Как готовиться к защите

Этот конспект рассчитан на защиту системы корпоративных закупок и на дополнительные вопросы по Java и Spring. Цель подготовки - уметь объяснить механизм, показать его в коде, назвать ограничение и предложить способ проверки. Простого перечисления аннотаций недостаточно.

Материал охватывает Java Core, ООП, проектирование, JDBC и SQL, Spring Framework, Spring Boot, MVC, Security, Data JPA, Hibernate, транзакции, тестирование и эксплуатацию. Экосистема Spring шире любого одного пособия: периферийные проекты рассмотрены обзорно, а механизмы, используемые в репозитории, подробно. Вопросы преподавателя заранее неизвестны; банк в конце помогает отработать основные направления и уточняющие вопросы.

## Рабочая схема ответа

- **Определение:** что означает термин без круговых формулировок.
- **Механизм:** кто создаёт объект, перехватывает вызов, выполняет SQL или проверяет права.
- **Пример:** конкретный класс или короткий фрагмент.
- **Ограничение:** когда решение не сработает или будет дорогим.
- **Проверка:** тест, SQL, лог, метрика либо наблюдаемый результат.

Например: «Транзакция объединяет изменения в атомарную операцию. В backend используется менеджер транзакций Spring и адаптер Transactions через TransactionTemplate. При изменении статуса заказа списание остатков и история должны согласованно завершиться или откатиться. Наличие аннотации само по себе не доказывает транзакционность: важны вызов через прокси, подключённый менеджер и используемый ресурс».

# 02. Архитектура вашего проекта

## Модули и направление зависимостей

`cps-core` содержит сущности, интерфейсы репозиториев, бизнес-сервисы, проверки и прямые Hibernate-реализации. `cps-console` и `cps-desktop` используют core; desktop работает на JavaFX. `cps-backend` подключает core и добавляет HTTP, Spring Data, безопасность, конфигурацию, поиск и аудит. Отдельный каталог `cps-web` содержит клиент React/Vite. В settings.gradle.kts включены четыре Java-модуля; наличие Android упомянуто в README, но это не доказывает готовую мобильную реализацию в данном checkout.

```text
Console / JavaFX -> cps-core -> Hibernate -> JDBC -> PostgreSQL

Web client -> HTTP -> cps-backend controllers
                       -> core services / backend services
                       -> Spring Data JPA / JdbcTemplate
                       -> Hibernate / JDBC -> PostgreSQL
```

**Почему это важно:** бизнес-правила можно использовать в нескольких интерфейсах. Core не требует Spring-контейнера для своих сервисов. Однако core зависит от JPA/Hibernate в модели и инфраструктуре, поэтому называть его полностью независимым от persistence-технологий было бы неточно.

## Слои и ответственность

| Элемент | Ответственность |
| --- | --- |
| Controller | HTTP, DTO, статусы, привязка параметров, вызов сценария. Не должен содержать SQL и расчёт остатков. |
| Service | Сценарий, бизнес-инварианты, координация репозиториев и транзакционная граница. |
| Repository | Чтение, запись и блокировки. Не принимает решений о разрешённых переходах статуса. |
| Entity | Состояние и локальные инварианты предметной модели, ORM-отображение. |
| DTO | Контракт входа/выхода API, независимый от полного графа ORM. |
| Configuration | Создание бинов и связывание реализаций интерфейсов. |

`ServicesConfig` создаёт core-сервисы через `@Bean`. Spring-репозиторий, например `SpringProductsRepository`, одновременно расширяет интерфейс core, `ListCrudRepository` и `JpaSpecificationExecutor`. Сервис знает контракт core; Spring подставляет реализацию-прокси. Это пример инверсии зависимостей и адаптации инфраструктуры.

## Транзакционная абстракция

Core использует интерфейс `Transactions`. Для console/desktop работает `HibernateTransactions`: активная Session хранится в ThreadLocal по SessionFactory, вложенные операции используют её повторно; при ошибке вложенная транзакция помечается rollback-only, ThreadLocal очищается. В backend бин `Transactions` делегирует в `TransactionTemplate` и менеджер Spring. Это позволяет выполнять один сценарий на разных инфраструктурах.

Нельзя смешать произвольную отдельно открытую Hibernate Session с транзакцией Spring и предположить, что они автоматически общие. Единство обеспечивают настроенные менеджер, DataSource и привязка ресурсов к текущему выполнению.

## Главные сущности

Пользователь создаёт заказ; заказ состоит из позиций; позиция ссылается на товар и хранит количество и закупочную цену; товар связан с категорией и тегами; остаток связывает товар и склад. История статусов и общий аудит решают разные задачи. В backend также есть учётные данные, refresh-сессии и использованные refresh-токены.

**Ключевые правила:** деньги представлены BigDecimal; остаток неотрицателен; пара товар/склад уникальна; CREATED и APPROVED резервируют товар; DELIVERED списывает физические остатки; доставленный заказ нельзя перевести в другой статус. Прочие переходы нужно описывать по фактическим условиям кода: полной строгой матрицы всех переходов в `transitionStock` нет.

**Что показать на защите:** BackendMain, ServicesConfig, OrdersController, OrdersServiceImpl, OrderStock, SpringProductsRepository, Product, миграции V17/V18, SecurityConfig и один содержательный интеграционный тест.

# 03. Java: платформа, типы и выполнение

## JDK, JVM и bytecode

Java - язык и платформа. `javac` компилирует исходный код в class-файлы с bytecode. JVM загружает и проверяет классы, выполняет код интерпретатором и JIT-компиляцией, управляет памятью и потоками. JDK включает инструменты разработки и runtime. JRE - понятие среды выполнения; современная поставка не обязательно содержит отдельный устанавливаемый продукт с таким названием.

Переносимость означает наличие совместимой JVM и зависимостей для целевой платформы. Нативные библиотеки, JavaFX, системные пути, кодировки и версия class-файла могут ограничивать запуск. Более старая JVM обычно не запускает bytecode более новой версии.

**Classpath** ищет классы и ресурсы. **Module path** используется системой модулей JPMS с `module-info.java`, `requires`, `exports`, `opens`. Gradle-модуль проекта и модуль JPMS - разные понятия. `exports` открывает публичный API, `opens` разрешает глубокую reflection в заданном объёме.

## Примитивы и ссылки

Восемь примитивов: byte, short, int, long, float, double, char, boolean. `char` - 16-битная кодовая единица UTF-16, не любой символ Unicode целиком. Числа с плавающей точкой не подходят для точной десятичной арифметики денег. Размер boolean как поля/элемента не задаётся простым правилом «один бит» на уровне Java.

Ссылочная переменная содержит ссылку либо null. Java всегда передаёт аргументы **по значению**. Для объекта копируется значение ссылки: можно изменить доступное изменяемое состояние объекта, но присваивание параметру новой ссылки не заменит переменную вызывающего кода.

```java
void rename(Product p) { p.setName("Paper"); }
void replace(Product p) { p = anotherProduct; }
// rename меняет объект; replace меняет локальный параметр.
```

Wrapper-типы Integer, Long и другие позволяют использовать значения в generics и хранить null. Autoboxing создаёт/получает wrapper, unboxing null вызывает NullPointerException. Сравнение wrapper через `==` сравнивает ссылки; кеширование части значений не меняет правило. Для nullable-объектов используйте Objects.equals.

## Преобразования и операторы

Расширяющее числовое преобразование может терять точность, например long -> double; сужающее требует явного cast и может менять значение. Целочисленное деление отбрасывает дробную часть. Обычное переполнение int/long не даёт автоматической ошибки; для контроля подходят Math.addExact и проверки диапазона до cast.

`&&` и `||` вычисляют правый операнд при необходимости; `&` и `|` с boolean вычисляют оба. `==` для объектов проверяет идентичность. `instanceof` проверяет совместимость типа и для null возвращает false. Условное выражение `?:` тоже имеет правила вывода типов и может вызвать неожиданную распаковку wrapper.

## Область видимости, static и final

`private`, package-private, `protected`, `public` управляют доступом. Protected вне пакета связан с наследованием и не означает «доступно любому через любой объект». Поле static принадлежит классу в соответствующем ClassLoader. Метод static не переопределяется полиморфно: в наследнике он скрывается.

Final-переменной нельзя повторно присвоить значение; final-ссылка не делает объект неизменяемым. Final-метод нельзя override, final-класс нельзя наследовать. `var` выводит статический тип локальной переменной и не превращает Java в динамически типизированный язык.

## Запуск и версия Java

Классическая точка входа - `public static void main(String[] args)`. В Java 25 допустимы расширенные формы main; поэтому package-private `static void main(String[] args)` в BackendMain не следует автоматически объявлять ошибкой. При обсуждении новых возможностей называйте целевую Java 25 и отличайте стабильные возможности от preview, требующих специальных флагов. Проверка версии: `java -version` и `./gradlew --version`.

# 04. ООП и модель предметной области

## Четыре опорных понятия

**Абстракция** выделяет существенный контракт и скрывает ненужные детали. Интерфейс OrdersRepository описывает операции, не заставляя сервис знать SQL. **Инкапсуляция** удерживает состояние и правила изменения вместе: setter остатка проверяет неотрицательность. Private без контроля выдаваемых mutable-коллекций ещё не обеспечивает полную инкапсуляцию.

**Наследование** выражает отношение подтипа и повторное использование поведения; оно создаёт сильную связь. **Полиморфизм** позволяет вызывать переопределённый метод по ссылке базового типа. Сервис получает ProductsRepository, а конкретная реализация выбирается конфигурацией.

## Интерфейс, абстрактный класс и композиция

Интерфейс задаёт тип и поведение; может иметь abstract, default, static и private методы, а поля являются public static final. Абстрактный класс может хранить экземплярное состояние, иметь конструкторы и методы разной видимости. Класс наследует один класс, но реализует несколько интерфейсов.

Композиция строит поведение из сотрудничающих объектов: OrdersServiceImpl содержит OrderStock и репозитории. Предпочтение композиции полезно, когда требуется менять стратегию без разрастания иерархии. Наследование уместно при устойчивом отношении «является» и соблюдении контракта подтипа.

| Механизм | Что решается |
| --- | --- |
| Overload | Выбор сигнатуры по статическим типам аргументов на этапе компиляции. Один только возвращаемый тип не различает перегрузки. |
| Override | Выбор реализации экземплярного метода по фактическому типу объекта во время выполнения. |
| Covariant return | Переопределение может вернуть более конкретный ссылочный тип. |
| Checked exceptions | Override не может расширить набор проверяемых исключений сверх разрешённого контрактом. |

## Конструкторы и инициализация

Конструктор создаёт начальное состояние, не имеет возвращаемого типа и не наследуется. Если свой конструктор объявлен, неявный конструктор без аргументов больше не добавляется. Для JPA он нужен отдельно. Статическая инициализация происходит при инициализации класса, затем при создании экземпляра выполняется инициализация экземплярных полей и конструкторная цепочка по правилам языка.

Не вызывайте переопределяемые методы из конструктора: наследник может ещё не завершить инициализацию. Не публикуйте `this` из конструктора до готовности инвариантов.

## Entity, Value Object, DTO

**Entity предметной области** имеет устойчивую идентичность во времени; изменение имени товара не превращает его в другой товар. **Value Object** определяется значением: Money(amount, currency), диапазон дат. **DTO** передаёт данные между границами, не обязан содержать бизнес-поведение. JPA entity - конкретное ORM-понятие; оно не совпадает автоматически со всеми DDD-терминами.

Record удобен для DTO и значений: компактный синтаксис, final-компоненты, сгенерированные equals/hashCode/toString. Неизменяемость record поверхностная: список внутри может оставаться mutable; делайте defensive copy. Обычная JPA entity по требованиям спецификации не является record.

## Инварианты и границы

Локальное правило «количество >= 0» проверяется внутри модели. Правило «заказ не резервирует больше доступного на нескольких складах» требует сервиса и транзакции. Правило «только менеджер меняет статус» требует проверки полномочий. CHECK и FK в БД защищают данные даже при обходе UI. Проверки на разных уровнях дополняют друг друга, если согласованы.

> Сильный ответ: «Я не просто применил ООП: интерфейсы отделяют бизнес-сценарии от хранения, композиция собирает сервис, а инварианты определяют допустимые изменения состояния».

# 05. Принципы кода и паттерны

## SOLID без заученных лозунгов

| Принцип | Смысл и пример |
| --- | --- |
| SRP | Одна связная ответственность и причина изменения. Контроллер меняется при изменении HTTP-контракта, расчёт резерва - при изменении бизнес-правила. |
| OCP | Новое поведение добавляется через предусмотренные расширения. Новая реализация репозитория не должна заставлять переписывать сервис. |
| LSP | Подтип сохраняет обещания контракта. Реализация getById не должна внезапно удалять запись или требовать более узкие входные условия. |
| ISP | Клиент зависит от нужного ему контракта. Огромный интерфейс всех операций системы затрудняет подмену и понимание. |
| DIP | Высокоуровневые правила зависят от абстракций. Core-сервис принимает интерфейс, инфраструктура реализует его. |

DIP - архитектурный принцип, DI - способ передачи зависимостей, IoC - более общая передача управления контейнеру/фреймворку. Эти понятия связаны, но не тождественны.

## Практические правила

**DRY** устраняет дублирование одного знания, а не любой похожей строки. **KISS** выбирает понятное решение достаточной сложности. **YAGNI** откладывает возможности без подтверждённой необходимости. Высокая связность внутри модуля и слабая связанность между модулями облегчают изменения.

Пишите имена по намерению: `requireAvailable` объясняет действие лучше `process`. Делайте методы небольшими по ответственности, а не по произвольному лимиту строк. Проверяйте аргументы на границе. Сохраняйте причину исключения. Комментируйте причины ограничений, например порядок блокировок; не пересказывайте очевидный код.

Возвращайте контрактный результат: Optional для возможного отсутствия, пустой список для отсутствия элементов, осмысленную ошибку для нарушенного сценария. Не возвращайте null там, где API обещает коллекцию. Избегайте глобального изменяемого состояния и скрытого чтения системного времени - Clock делает время подменяемым в тесте.

## Часто используемые паттерны

- **Repository / DAO:** изоляция доступа к данным; Repository обычно выражает коллекцию доменных объектов, DAO - операции хранения. Граница терминов зависит от архитектуры.
- **Service Layer:** реализация прикладного сценария и его координации.
- **Strategy:** подстановка алгоритма через общий интерфейс, например способ экспорта или хранения.
- **Adapter:** Transactions связывает контракт core с TransactionTemplate; Spring-репозиторий связывает контракт core с Data JPA.
- **Factory:** централизованное создание объектов с нужной конфигурацией; `@Bean` - метод конфигурации создания бина.
- **Proxy:** посредник добавляет транзакции, безопасность или кэш к вызову целевого объекта.
- **Template Method / Template:** общий алгоритм оставляет изменяемую часть callback; JdbcTemplate управляет ресурсами и вызывает RowMapper.
- **Builder:** пошаговое создание сложного значения, например JwtClaimsSet.
- **Observer / Events:** издатель сообщает о факте, слушатель реагирует; событие не обязано означать отдельный поток.

## Архитектурные компромиссы

Многослойность не делает систему автоматически clean architecture. Сущности core используют ORM-аннотации, некоторые HTTP-операции держат транзакцию на контроллере, а часть core-чтений фильтрует getAll в памяти. Это фактические решения с последствиями: повторное использование удобно, но инфраструктурная связанность и стоимость больших выборок остаются.

Рефакторинг должен отвечать на конкретную проблему: перенести сценарную транзакцию в фасад-сервис, добавить запрос по фильтру вместо getAll, ввести проверку владения ресурсом или выделить DTO-проекцию. Не обещайте «идеальную архитектуру» и не называйте каждый дополнительный интерфейс улучшением.

# 06. Object, строки, деньги и время

## equals и hashCode

`Object.equals` по умолчанию соответствует идентичности объекта. Для равенства по значению переопределяют equals и hashCode согласованно. Equals должен быть рефлексивным, симметричным, транзитивным, стабильным при неизменном значимом состоянии и возвращать false для null. Если объекты равны, их hashCode одинаков. Обратное неверно: коллизии допустимы.

HashMap сначала использует hash для выбора области поиска, затем equals для различения ключей. Изменение значимого поля ключа после добавления может сделать запись недоступной обычным поиском. Константный hashCode формально возможен, но ухудшает распределение; плохое распределение влияет на производительность.

Для JPA entity равенство сложнее: generated id может отсутствовать до сохранения, proxy может иметь другой runtime-класс, связи могут загружаться лениво. Нельзя механически генерировать equals/hashCode по всем полям. Возможны устойчивый business key либо аккуратная стратегия идентификатора с учётом transient-состояния и прокси; выбор должен быть единым и протестированным. В данном Product equals/hashCode не переопределены: коллекция Set использует объектную идентичность.

## String и StringBuilder

String неизменяем, поэтому подходит для ключей, безопасного совместного чтения и intern pool. Строковый литерал и `new String(...)` могут ссылаться на разные объекты с одинаковым содержимым. Сравнивайте текст через equals. `StringBuilder` изменяем и удобен для многократного построения строки в одном потоке; `StringBuffer` синхронизирует операции, но редко нужен в обычной сборке ответа.

`length()` считает UTF-16 code units, а не пользовательские графемы. Обрезка по char может разорвать surrogate pair; сложные символы могут включать несколько code points. Явно задавайте UTF-8 при обмене файлами и HTTP. Не путайте экранирование JSON, SQL-параметры и HTML-экранирование: они решают разные задачи.

## BigDecimal и деньги

```java
BigDecimal a = new BigDecimal("0.10");
BigDecimal total = a.multiply(BigDecimal.valueOf(quantity));
BigDecimal shown = total.setScale(2, RoundingMode.HALF_UP);
boolean sameAmount = a.compareTo(new BigDecimal("0.1")) == 0;
```

`new BigDecimal(0.1)` сохраняет особенности исходного double; строка или valueOf обычно выражают десятичное намерение лучше. BigDecimal неизменяем: результат add/multiply нужно использовать. Equals учитывает scale, поэтому 1.0 и 1.00 могут быть не равны; compareTo сравнивает числовые значения. Деление без правила округления может выбросить ArithmeticException для бесконечной десятичной дроби.

Precision - число значащих цифр, scale - число цифр после десятичной точки. Для NUMERIC(10,2) остаётся восемь цифр целой части. Валюта, допустимое округление, минимальная единица и момент округления - бизнес-правила. В позиции заказа нужна зафиксированная purchasePrice: изменение текущей цены каталога не должно переписать историю суммы.

## java.time

Instant - момент на временной шкале; LocalDate - календарная дата; LocalDateTime - дата/время без зоны; OffsetDateTime содержит смещение, ZonedDateTime также использует правила зоны. Duration выражает длительность, Period - календарный период. Clock позволяет заменить текущее время фиксированным в тесте.

Не храните момент события как LocalDateTime без договорённости о зоне. PostgreSQL TIMESTAMPTZ представляет момент, а исходное имя зоны отдельно не сохраняет. В проекте сущности используют Instant, конфигурация JDBC задаёт Europe/Moscow, а JWT-валидация использует UTC Clock. Это совместимо при корректном преобразовании; формат отображения и момент хранения - разные вещи.

**Типичный вопрос:** «Почему пароль нельзя положить в toString?» Логи могут сохраняться дольше запроса и быть доступны операторам. DTO, entity и record с секретами требуют контроля журналирования; автоматически сгенерированный toString тоже может раскрыть поля.

# 07. Коллекции и generics

## Основные контракты

| Тип | Свойства и применение |
| --- | --- |
| List | Упорядоченная последовательность, дубликаты разрешены, доступ по индексу. |
| Set | Уникальность по контракту равенства; порядок зависит от реализации. |
| Queue / Deque | Очередь, стек, двусторонние операции; ArrayDeque удобен без синхронизации. |
| Map | Ключ -> значение; не наследует Collection. Уникальны ключи, значения могут повторяться. |
| SortedSet / SortedMap | Порядок задаёт Comparable или Comparator. Согласуйте сравнение с equals. |

ArrayList хранит массив ссылок: get O(1), добавление в конец амортизированно O(1), вставка/удаление в середине O(n). LinkedList имеет узлы: поиск позиции O(n); O(1) для вставки относится к уже известной позиции/концу и не делает произвольные операции быстрее ArrayList. Накладные расходы и locality часто важнее формальной сложности.

HashMap/HashSet дают ожидаемую O(1) базовых операций при хорошем распределении; TreeMap/TreeSet - O(log n). LinkedHashMap/LinkedHashSet сохраняют определённый порядок обхода. ConcurrentHashMap подходит для конкурентного доступа, не разрешает null и поддерживает атомарные составные методы compute/merge. Обычный HashMap нельзя безопасно менять несколькими потоками без координации.

## Неизменяемость и итерация

`List.of` и `List.copyOf` создают неизменяемую по структуре коллекцию и не принимают null. `Collections.unmodifiableList` - представление: изменение исходного списка может отражаться в нём. Ни то ни другое само по себе не замораживает объекты-элементы. `Arrays.asList` - список фиксированного размера на массиве; set допустим, add/remove обычно нет.

Fail-fast iterator может выбросить ConcurrentModificationException при структурном изменении не через него; это диагностический механизм, а не гарантия потокобезопасности. Для удаления при обходе используйте iterator.remove или removeIf согласно контракту. Не путайте поток Stream с потоком выполнения Thread.

## Обобщения

Generics обеспечивают проверку типов при компиляции. `List<Integer>` не является подтипом `List<Number>`: иначе туда можно было бы добавить Double. Массивы ковариантны и могут дать ArrayStoreException; generics в основном инвариантны и обнаруживают подобное раньше.

```java
double sum(List<? extends Number> values) {
    return values.stream().mapToDouble(Number::doubleValue).sum();
}
void addIds(List<? super UUID> target, UUID id) {
    target.add(id);
}
```

Правило PECS: producer extends, consumer super. Из `? extends T` безопасно читать T, но нельзя добавить произвольный T. В `? super T` можно добавлять T, а чтение гарантирует только Object. `List<?>` - список неизвестного конкретного типа; raw List отключает часть проверок и создаёт риск heap pollution.

Type erasure стирает многие сведения о параметрах в исполняемом коде: нельзя `new T()`, `new List<String>[n]` или `instanceof List<String>`. При этом generic-сигнатуры деклараций могут присутствовать в метаданных, поэтому утверждение «reflection совсем ничего не знает о generics» неверно.

## Частые ловушки

Comparator должен соблюдать транзитивность; вычитание `a - b` для сравнения может переполниться, используйте Integer.compare. `toMap` без merge-функции падает на повторном ключе. Для агрегации количеств в проекте используется Map.merge; длинные суммы хранятся в long, а перед преобразованием обратно в int проверяется предел.

# 08. Исключения, I/O и ресурсы

## Иерархия и смысл ошибок

Throwable разделяется на Error и Exception. RuntimeException и её подклассы - непроверяемые; остальные Exception обычно checked. Checked требует catch или throws. Error обычно означает серьёзную проблему выполнения; перехватывать и скрывать её для продолжения обычной работы не следует.

Исключения должны отражать смысл: неверный аргумент, отсутствующая сущность, конфликт состояния, инфраструктурная недоступность. Не превращайте все ошибки в 400: сломанная БД и неверная цена - разные ситуации. Сохраняйте cause и не возвращайте SQL, stack trace и секреты клиенту.

`throw` выбрасывает конкретное исключение, `throws` объявляет возможность. Catch выбирается от более конкретного типа к общему. Finally выполняется при обычном выходе и большинстве исключений, но не гарантирован при аварийной остановке процесса. Return/throw из finally способен подавить первоначальный результат или ошибку.

## try-with-resources

```java
try (Connection c = dataSource.getConnection();
     PreparedStatement ps = c.prepareStatement(
         "select name from products where id = ?")) {
    ps.setObject(1, id);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) return rs.getString("name");
    }
}
```

Ресурс реализует AutoCloseable. Закрытие идёт в обратном порядке объявления. Если основная операция уже бросила ошибку, ошибка close может стать suppressed; её можно получить через getSuppressed. Нельзя полагаться на GC для освобождения соединения или файлового дескриптора.

Connection из пула при close обычно возвращается в пул. Закрытие ссылки не обязательно закрывает физический сокет БД. Соединение, ResultSet и statement обычно не предназначены для произвольного совместного использования потоками.

## Файлы и потоки

InputStream/OutputStream работают с байтами, Reader/Writer - с символами и кодировкой. Buffering уменьшает число обращений к источнику. NIO Path/Files удобны для путей и операций; чтение всего файла в память подходит только для ограниченного размера. Потоки от Files.lines и похожих API требуют закрытия.

CSV нельзя корректно обрабатывать простым split(","): поля могут содержать разделители, кавычки и переводы строк. Нужен CSV-парсер и явная кодировка. При экспорте для электронных таблиц учитывают формулы, начинающиеся с `=`, `+`, `-`, `@`; безопасная обработка зависит от целевого формата и сценария. Не считайте универсальным один только запрет запятой.

## Сериализация

JSON - внешний формат данных; ORM persistence - сохранение модели; Java Serializable - отдельный механизм сериализации объектов. `transient` Java не равен JPA `@Transient` и не является универсальной защитой от попадания поля в JSON. Настройки JSON и DTO определяют, что уходит в HTTP.

Нативная десериализация недоверенных Java-объектов опасна. Для API используйте ограниченные схемы DTO, лимиты размера и глубины, валидацию; не разрешайте произвольные типы из входного сообщения. Изменение схемы требует контроля совместимости клиентов.

# 09. Функциональные возможности и современная Java

## Lambda и функциональные интерфейсы

Функциональный интерфейс имеет один абстрактный метод с учётом правил наследования; default/static методы не мешают. `@FunctionalInterface` позволяет компилятору проверить намерение. Lambda реализует такой контракт, а ссылка на метод - краткая запись подходящего вызова.

| Контракт | Назначение |
| --- | --- |
| Supplier<T> | Получить T без аргументов. |
| Consumer<T> | Выполнить действие над T без результата. |
| Function<T,R> | Преобразовать T в R. |
| Predicate<T> | Проверить условие над T. |
| UnaryOperator<T> | Преобразовать T в T. |

Lambda захватывает локальные переменные, которые final или effectively final. Это ограничивает переприсваивание переменной, но не гарантирует неизменяемость захваченного объекта. Checked exception нельзя свободно выбросить из Function, если его метод её не объявляет.

## Stream API

Stream строит pipeline: source -> промежуточные операции -> terminal operation. Filter/map обычно ленивы; collect, reduce, count, forEach и toList запускают вычисление. Stream одноразовый. `map` преобразует элементы, `flatMap` разворачивает вложенные потоки, `peek` не предназначен для обязательной бизнес-логики.

```java
BigDecimal total = lines.stream()
    .map(x -> x.price().multiply(BigDecimal.valueOf(x.quantity())))
    .reduce(BigDecimal.ZERO, BigDecimal::add);
```

Reduce требует согласованной ассоциативной операции, особенно при параллельном исполнении. Побочные изменения общего ArrayList внутри parallelStream создают гонку. ParallelStream использует инфраструктуру параллелизма, но не обещает ускорение; блокирующий JDBC и контекст транзакции не следует автоматически переносить туда.

`Stream.toList()` возвращает unmodifiable list. `Collectors.toList()` не обещает конкретную реализацию или все характеристики изменяемости; если нужен конкретно ArrayList, используйте toCollection(ArrayList::new). Encounter order и порядок фактического выполнения - не одно и то же.

## Optional

Optional выражает возможное отсутствие результата. `map` преобразует значение, `flatMap` нужен, если функция уже возвращает Optional. `orElse` вычисляет аргумент заранее, `orElseGet` - только при отсутствии. `get()` без проверки уничтожает ясность контракта; обычно лучше orElseThrow.

Optional не является универсальной заменой каждого nullable-поля, параметра и JPA-связи. Не возвращайте null вместо самого Optional. Для списка отсутствие записей обычно означает пустой список, а не Optional<List<T>>.

## Records, enums, sealed и pattern matching

Enum задаёт закрытый набор именованных экземпляров, может иметь поля и поведение. EnumType.STRING устойчивее ORDINAL к перестановке констант, но переименование строкового значения требует миграции. Switch expression возвращает значение; исчерпывающий switch над enum/sealed типом помогает обнаруживать неполную обработку.

Sealed ограничивает допустимых прямых наследников; final/non-sealed/sealed фиксируют дальнейшую политику. Pattern matching уменьшает ручные cast. В проекте AuditEntityListener использует switch по типам entity, а DTO часто оформлены как records. Не приписывайте этим возможностям автоматическую потокобезопасность.

Современная Java также развивает virtual threads, scoped values и структурную конкурентность. Их статус зависит от версии. Для защиты важнее понимать стоимость I/O, отмену задач, контексты и ограничения БД, чем перечислять все JEP. Preview-функции нельзя выдавать за стабильный обязательный API.

# 10. Аннотации и reflection

## Что такое аннотация

Аннотация - метаданные у декларации или использования типа. Она сама не выполняет действие. Поведение реализует компилятор, annotation processor, библиотека, контейнер, ORM или тестовый runner. `@Override` проверяется компилятором, `@Entity` читается ORM, `@Transactional` - транзакционной инфраструктурой Spring.

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Audited {
    String value() default "change";
}
```

Элементы аннотации ограничены разрешёнными типами: примитивы, String, Class, enum, другие аннотации и их массивы. Это не произвольные методы с телом. Наличие собственной @Audited не создаст аудит, пока никто её не обработает.

## Метааннотации

| Аннотация | Смысл |
| --- | --- |
| @Retention | SOURCE - только исходный код; CLASS - class-файл; RUNTIME - доступна reflection. По умолчанию CLASS. |
| @Target | Допустимые места: TYPE, METHOD, FIELD, PARAMETER, TYPE_USE и другие. |
| @Documented | Участие в генерируемой документации. |
| @Inherited | Наследование аннотации класса от superclass при соответствующем поиске; не универсальное наследование методов и интерфейсов. |
| @Repeatable | Разрешает повторение через контейнерную аннотацию. |

Составная аннотация объединяет метаданные других аннотаций. В Spring есть собственные правила поиска merged/meta-annotations и alias-атрибутов; они шире примитивной проверки `getAnnotation` одного элемента.

## Reflection и dynamic proxy

Reflection получает Class, поля, методы, конструкторы и аннотации во время выполнения. Позволяет динамически создавать объект и вызывать метод, но уменьшает статическую проверяемость, учитывает ограничения доступа и JPMS, создаёт накладные расходы и требует конфигурации при некоторых AOT-сценариях.

ClassLoader загружает классы; одинаковое полное имя в разных загрузчиках может означать разные типы. Reflection не означает право бесконтрольно читать любое private-поле: современная модульная инкапсуляция может запретить доступ.

JDK dynamic proxy реализует интерфейсы и направляет вызов в InvocationHandler. Class-based proxy создаёт подкласс, поэтому упирается в final-класс и final/private методы. ORM-прокси для lazy-связей и Spring AOP-прокси решают разные задачи, хотя внешне оба являются посредниками.

## Три разных вида @NotNull

`jakarta.validation.constraints.NotNull` - runtime constraint при запуске Bean Validation. JetBrains `@NotNull` прежде всего описывает контракт для инструментов; сам по себе не обязан выполнять проверку входа. JSpecify `@NonNull` - сведения о nullness для анализа и связанных инструментов. `@Column(nullable=false)` относится к mapping/DDL, а не автоматически к каждой форме HTTP.

В проекте присутствуют все эти семейства. Поэтому ответ «все @NotNull делают одно и то же» неверен. Реальная защита зависит от импорта, момента запуска проверки и ограничений БД. Официальная база по формату аннотаций: [Oracle Annotations Basics](https://docs.oracle.com/javase/tutorial/java/annotations/basics.html).

# 11. JVM, память и многопоточность

## Память и сборка мусора

Heap содержит объекты и массивы в модели выполнения; стек потока содержит кадры вызовов и локальные значения. Реализация JVM может оптимизировать размещение и устранять выделения, поэтому «каждый объект всегда физически лежит в heap» - слишком грубое объяснение. Metaspace хранит метаданные классов вне обычного Java heap.

GC освобождает недостижимые объекты. Цикл ссылок без пути от GC roots не спасает объекты от сборки. Memory leak в Java возможен: статический Map, забытый listener, ThreadLocal, неограниченный кэш удерживают ненужные объекты достижимыми. OutOfMemoryError бывает связан не только с heap. StackOverflowError обычно возникает из-за чрезмерной глубины вызовов.

Не полагайтесь на finalize для ресурсов. Профилируйте до оптимизации: heap dump показывает удержание объектов, thread dump - стеки/ожидания, JFR - события выполнения, GC logs - поведение сборщика. Логи SQL помогают найти количество запросов, но не заменяют измерение задержки и плана БД.

## Атомарность, видимость и порядок

Race condition возникает, когда результат зависит от неконтролируемого чередования. `count++` - чтение, вычисление и запись, а не единая атомарная операция. `volatile` обеспечивает видимость и определённые гарантии порядка, но не делает increment атомарным. AtomicInteger решает отдельные атомарные операции; составные бизнес-инварианты требуют более широкой координации.

Synchronized обеспечивает взаимное исключение по монитору и happens-before между освобождением и последующим захватом. Lock даёт гибкое управление, tryLock/interruptible lock, но требует unlock в finally. Deadlock - цикл ожидания ресурсов; общий порядок захвата снижает риск. Livelock и starvation - другие проблемы прогресса.

## Executor, Future и отмена

ExecutorService отделяет задачу от управления потоками. Размер пула и очереди ограничивает нагрузку; бесконечная очередь может скрыть перегрузку до нехватки памяти. Future хранит результат, CompletableFuture позволяет композицию стадий. Исключения фоновых задач нужно наблюдать, а executor корректно завершать.

Interrupt - кооперативный сигнал. После InterruptedException обычно следует восстановить флаг через Thread.currentThread().interrupt(), если обработка не завершается передачей исключения выше. Timeout ожидания результата не гарантирует остановку самой операции; нужны отмена и таймауты ресурса.

## Контексты и Spring

Singleton-бин обслуживает многие запросы: хранить в его поле текущего пользователя, EntityManager конкретной операции или mutable request state опасно. ThreadLocal не переносится автоматически на любой новый поток и требует очистки при повторном использовании потоков. Это относится к транзакциям, MDC и SecurityContext с учётом конкретной инфраструктуры.

SessionFactory/EntityManagerFactory рассчитаны на совместное использование. Конкретная Hibernate Session/EntityManager - единица работы, не потокобезопасный общий объект. Внедрённая Spring-ссылка EntityManager обычно является делегирующим посредником к ресурсу текущего контекста.

## Virtual threads

Virtual threads облегчают большое число I/O-задач в привычном блокирующем стиле. Они не ускоряют CPU-вычисления и не создают дополнительные соединения PostgreSQL. Пул БД, лимиты параллелизма и backpressure всё равно нужны. Обычно virtual thread создаётся на задачу, а не кладётся в фиксированный пул ради экономии самих virtual threads.

Правила конкурентности Java сохраняются: два virtual thread так же могут иметь гонку. Включение virtual threads не делает JPA реактивным. Сведения по Java 25: [Oracle Virtual Threads](https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html).

# 12. SQL и реляционная модель

## Таблицы, ключи и нормализация

Первичный ключ идентифицирует строку, внешний ключ обеспечивает ссылочную целостность, UNIQUE запрещает дубликаты по заданным правилам, NOT NULL требует значение, CHECK проверяет допустимость строки. UUID помогает генерировать идентификаторы без центрального счётчика, но требует места и не отменяет индексы и ограничения.

Первая нормальная форма предполагает атомарные значения в выбранной модели; вторая убирает частичные зависимости от составного ключа, третья - транзитивные зависимости неключевых атрибутов. Нормализация уменьшает аномалии изменения. Денормализация допустима как осознанное решение для скорости или истории, например purchasePrice в позиции заказа.

Связь many-to-many реализуется таблицей соединения. Если у связи появляются собственные атрибуты, её часто оформляют отдельной сущностью. `inventory(product_id, warehouse_id, quantity)` - сущность связи с количеством; уникальность пары предотвращает две записи остатка одного товара на одном складе.

## SELECT, JOIN, GROUP BY

```sql
SELECT o.id, COALESCE(SUM(i.quantity * i.purchase_price), 0) total
FROM orders o
LEFT JOIN order_items i
  ON i.order_id = o.id AND i.deleted_at IS NULL
WHERE o.deleted_at IS NULL
GROUP BY o.id
ORDER BY o.id;
```

INNER JOIN оставляет совпадения; LEFT JOIN сохраняет строки слева без пары. Условие на правую таблицу в WHERE может удалить строки без совпадения и изменить смысл LEFT JOIN. WHERE фильтрует строки до группировки, HAVING - группы после неё. COUNT(*) считает строки, COUNT(column) пропускает null. SUM по пустому набору возвращает null; COALESCE задаёт замену.

SQL использует трёхзначную логику: сравнение с null не даёт обычного true/false. Пишите IS NULL/IS NOT NULL. `NOT IN` при null в подзапросе может дать неожиданный результат; рассмотрите NOT EXISTS с ясной семантикой.

## Индексы и планы

B-tree подходит для многих равенств и диапазонов. Составной индекс выбирают по фильтрам, сортировке и распределению данных; порядок колонок важен. Индекс ускоряет часть чтений, но занимает место и увеличивает стоимость записей. Функция над колонкой или поиск по `%term%` не обязаны использовать обычный B-tree; может потребоваться функциональный индекс либо специальный тип индекса.

EXPLAIN показывает оценочный план, EXPLAIN ANALYZE выполняет запрос и показывает фактические данные. Последний нельзя бездумно применять к изменяющим запросам. Seq scan не всегда плох: для большой доли таблицы он может быть дешевле индекса. Оценивайте rows, loops, selectivity, buffers, сортировку и актуальность статистики.

FK не означает, что любой полезный индекс на ссылающейся колонке уже создан. Добавляйте индексы миграциями под реальные запросы, а не только аннотациями в entity при ddl-auto=validate.

## Пагинация и конкурентность

LIMIT/OFFSET без ORDER BY не гарантирует воспроизводимых страниц. Даже с сортировкой по неуникальной дате нужен tie-breaker, например id. Большой OFFSET дорог; keyset pagination продолжает после последнего ключа и подходит для последовательного просмотра. Стабильный ORDER BY не фиксирует весь набор при конкурентных вставках и удалениях.

Транзакция и блокировки нужны для read-modify-write: два клиента могут прочитать один остаток и оба решить, что товара достаточно. Уникальный constraint решает дубликаты, но не любую гонку резерва. Уровни изоляции и стратегии блокирования разобраны в разделах 25-26.

# 13. JDBC и Spring JDBC

## Объекты JDBC

JDBC - стандартный API Java для доступа к реляционным БД через драйвер. Driver переводит вызовы в протокол конкретной БД. DataSource предоставляет соединения; Connection представляет сессию взаимодействия, Statement/PreparedStatement выполняет SQL, ResultSet читает строки. JDBC сам по себе не является ORM.

`executeQuery` возвращает ResultSet, `executeUpdate` - количество затронутых строк для обычных DML, `execute` поддерживает общий случай результатов. ResultSet изначально стоит до первой строки; next продвигает курсор. Индексы параметров и колонок JDBC начинаются с 1.

PreparedStatement отделяет значения от текста запроса и защищает от SQL injection при правильном использовании. Параметром нельзя подставить имя таблицы, колонки или направление ORDER BY; такие части выбирают по allowlist. Утверждение «PreparedStatement всегда быстрее» слишком сильное: подготовка/кеширование зависят от драйвера, сервера и повторного использования.

## Транзакция вручную: учебный пример

```java
try (Connection c = dataSource.getConnection()) {
    c.setAutoCommit(false);
    try {
        try (PreparedStatement ps = c.prepareStatement(
                "update inventory set quantity = quantity - ? "
                + "where id = ? and quantity >= ?")) {
            ps.setInt(1, amount);
            ps.setObject(2, inventoryId);
            ps.setInt(3, amount);
            if (ps.executeUpdate() != 1)
                throw new IllegalStateException("Insufficient stock");
        }
        c.commit();
    } catch (SQLException | RuntimeException e) {
        try { c.rollback(); }
        catch (SQLException rollbackFailure) {
            e.addSuppressed(rollbackFailure);
        }
        throw e;
    }
}
```

Пример работает с выделенным соединением из корректно настроенного пула и не должен копироваться внутрь Spring-транзакции: там commit/rollback делает менеджер. В реальном коде учитывают восстановление состояния при повторном использовании соединения, инфраструктурные ошибки commit и требования конкретного пула. Условный UPDATE защищает одну строку; межтабличный резерв требует полного сценария.

Auto-commit обычно включён на новом JDBC Connection: каждый statement завершается самостоятельно по правилам драйвера. Для нескольких согласованных изменений его отключают и явно завершают транзакцию. Savepoint позволяет частичный откат, если драйвер и менеджер это поддерживают. Основы: [Oracle JDBC Transactions](https://docs.oracle.com/javase/tutorial/jdbc/basics/transactions.html).

## Ошибки, batching и пул

SQLException содержит SQLState, vendor code и цепочку причин. По состоянию можно отличить unique violation от недоступности ресурса. Batch через addBatch/executeBatch уменьшает сетевые вызовы; результат может частично выполниться согласно правилам драйвера и транзакции. Для сгенерированных ключей используют generated keys или возможности СУБД.

Пул HikariCP переиспользует физические соединения. Важны maximumPoolSize, ожидание выдачи соединения, lifetime и таймауты. Больше соединений не обязательно означает большую пропускную способность: БД имеет ограниченные CPU, I/O и память. Сетевые/statement/query/transaction timeout - разные уровни; один параметр не покрывает все зависания.

## JdbcTemplate и NamedParameterJdbcTemplate

JdbcTemplate управляет шаблонным JDBC-кодом, освобождением ресурсов и переводит SQLException в DataAccessException. RowMapper преобразует одну строку в объект; он не должен выполнять дополнительный запрос для каждой строки. NamedParameterJdbcTemplate позволяет именованные параметры и удобную передачу наборов значений.

```java
List<ProductRow> rows = jdbc.query(
    "select id, name from products where price >= ?",
    (rs, n) -> new ProductRow(
        rs.getObject("id", UUID.class), rs.getString("name")),
    minPrice);
```

В проекте JdbcStatisticsRepository выполняет агрегации SQL сразу в DTO, а AuditEventWriter вставляет аудит через JdbcTemplate. JDBC может участвовать в той же локальной транзакции, что JPA, если использует согласованные DataSource и JpaTransactionManager. При чтении через JDBC после несброшенных JPA-изменений может понадобиться flush: JDBC не читает память persistence context.

# 14. Spring Framework: карта и IoC

## Что именно называется Spring

Spring Framework предоставляет контейнер объектов, DI, AOP, абстракции транзакций, доступ к данным, MVC/WebFlux, события и интеграционные возможности. Spring Boot собирает приложение с условной автоконфигурацией, управлением зависимостями и удобным запуском. Spring Data предоставляет семейство абстракций доступа к данным. Spring Security решает аутентификацию, авторизацию и защиту запросов. JPA - отдельная спецификация Jakarta; Hibernate - её провайдер.

```text
Spring Boot -> конфигурация приложения и runtime
Spring Framework -> IoC, AOP, MVC, transactions, JDBC
Spring Data JPA -> repository proxy -> EntityManager
Hibernate -> ORM и SQL -> JDBC driver -> PostgreSQL
Spring Security -> проверка запросов и вызовов методов
```

Framework отличается от библиотеки тем, что задаёт цикл работы и вызывает пользовательские компоненты в предусмотренных точках. Это одна из форм inversion of control. Bean - объект, создание и/или жизненный цикл которого контролирует контейнер. Объект, созданный `new` в произвольном коде, не становится Spring-бином только из-за аннотации на классе.

## BeanFactory и ApplicationContext

BeanFactory - базовый контракт получения и управления бинами. ApplicationContext расширяет модель: события, ресурсы, сообщения, интеграция с Environment и инфраструктурой приложения. Большинство обычных Boot-приложений работает с ApplicationContext. ApplicationContext может иметь родителя; singleton уникален в контексте определения бина, а не во всей JVM.

**BeanDefinition** описывает рецепт: класс/фабрику, scope, зависимости, init/destroy. Сначала регистрируются определения и обрабатываются настройки, затем создаются экземпляры по необходимости и правилам контейнера. Прокси, возвращаемый контейнером, может отличаться от исходного target-object.

## Регистрация компонентов

`@Component` - общий стереотип. `@Service` обозначает сервисную роль, `@Repository` - слой хранения и участие в инфраструктуре перевода исключений при её настройке, `@Controller` - MVC-компонент, `@RestController` добавляет семантику response body. Они помогают сканированию и читаемости, но не меняют бизнес-логику магически.

`@Bean` регистрирует результат фабричного метода; полезен для сторонних классов и явной сборки. `@Import` подключает конфигурацию/компоненты. XML-конфигурация всё ещё возможна, хотя в проекте используются Java-конфигурации и Boot.

Сканирование компонентов, JPA-сущностей и Spring Data repositories - разные процессы. `@Entity` не равно `@Component`. В BackendMain `@EntityScan` явно включает пакеты core и backend, потому что core расположен вне дерева `com.team.corporate.backend`. Core-сервисы подключены `@Bean`, а не автоматически найдены как `@Service`.

## Что происходит при запуске

Упрощённая последовательность: SpringApplication готовит Environment, создаёт context, загружает bean definitions и автоконфигурации, применяет post-processors, создаёт нужные singleton, поднимает web-инфраструктуру, завершает refresh, запускает runners и публикует события готовности. Точные события/порядок отдельных инфраструктур зависят от типа приложения.

Не делайте в конструкторе бина долгую сетевую работу без необходимости. Разделяйте создание объекта, инициализацию инфраструктуры и прикладные действия после старта. Общая отправная точка: [Spring IoC Container](https://docs.spring.io/spring-framework/reference/core/beans.html).

# 15. DI, scope и жизненный цикл бина

## Внедрение зависимостей

Constructor injection делает обязательные зависимости явными и допускает final-поля. В тесте сервис можно создать без Spring. Если у бина один конструктор, `@Autowired` обычно не нужен. Setter injection подходит для действительно необязательной/изменяемой зависимости; field injection скрывает требования объекта и усложняет обычное создание.

```java
@Service
class CatalogFacade {
    private final ProductsRepository products;
    CatalogFacade(ProductsRepository products) {
        this.products = products;
    }
}
```

При нескольких кандидатах важны тип, qualifier и другие правила разрешения. `@Primary` выделяет предпочтительный бин, `@Qualifier` сужает выбор по метке; qualifier не всегда просто имя. `@Order` задаёт порядок там, где инфраструктура его учитывает, и не заменяет выбор единственного кандидата. Внедрение List<T> получает набор реализаций.

`ObjectProvider<T>` позволяет отложенное или необязательное получение. `@Lazy` может отложить создание/дать прокси; это не исправляет плохую зависимость по смыслу. Цикл конструкторов обычно неразрешим; вместо автоматического обхода перепроектируйте ответственность или выделите третий компонент.

## Scopes

| Scope | Граница экземпляра |
| --- | --- |
| singleton | Один экземпляр на bean definition в контейнере; scope по умолчанию. |
| prototype | Новый экземпляр при запросе у контейнера; полный destroy lifecycle контейнер не ведёт. |
| request | Один экземпляр на HTTP request в web-контексте. |
| session | На HTTP session. Не связан напрямую с refresh-сессией в таблице БД. |
| application | На ServletContext. |
| websocket | На WebSocket session при соответствующей инфраструктуре. |

Если prototype внедрён прямо в singleton через конструктор, контейнер разрешит его в момент создания singleton; новый объект на каждый вызов не появится. Для этого нужен provider, lookup или scoped proxy. Singleton не означает thread-safe: поля бина должны учитывать параллельные запросы. Подробнее: [Bean Scopes](https://docs.spring.io/spring-framework/reference/core/beans/factory-scopes.html).

## Lifecycle: что происходит с экземпляром

Типичная схема: создание -> заполнение зависимостей -> Aware callbacks -> BeanPostProcessor before initialization -> `@PostConstruct` и другие init callbacks -> BeanPostProcessor after initialization, где часто формируется итоговая прокси-обёртка -> использование -> `@PreDestroy`/destroy при корректном закрытии контекста.

BeanFactoryPostProcessor изменяет определения до обычного создания бинов. BeanPostProcessor работает с экземплярами. `@PostConstruct` вызывается после injection, но обычный вызов собственного transactional-метода оттуда не гарантирует AOP-перехват. Не запускайте бизнес-транзакции на предположении, что финальный прокси уже участвует во внутренних вызовах.

`@DependsOn` задаёт зависимость инициализации; это не общий механизм сортировки всех операций приложения. SmartLifecycle используется для компонентов с start/stop. CommandLineRunner/ApplicationRunner удобны для действий после создания context; ApplicationRunner даёт структурированные arguments.

## @Configuration и proxyBeanMethods

В полной `@Configuration` с proxyBeanMethods=true вызовы `@Bean`-методов через усиленный конфигурационный объект могут разрешаться контейнером с сохранением scope. При `proxyBeanMethods=false` прямой вызов метода в Java - обычный вызов и может создать лишний объект.

В проекте используется `@Configuration(proxyBeanMethods=false)` и параметры `@Bean`-методов для зависимостей. Это хорошо объяснимо: контейнер передаёт нужный бин, прямые межметодные вызовы не требуются. FactoryBean<T> - отдельный контракт создания продукта; он не равен BeanFactory. Ссылка с `&name` обращается к самой фабрике в соответствующем API.

Источники для уточнения порядка: [Bean lifecycle](https://docs.spring.io/spring-framework/reference/core/beans/factory-nature.html), [Java configuration](https://docs.spring.io/spring-framework/reference/core/beans/java/basic-concepts.html).

# 16. AOP и прокси

## Термины и назначение

AOP выделяет сквозные задачи: транзакции, безопасность, метрики, кэширование, аудит. Aspect объединяет правило и действие; join point - точка выполнения, pointcut - условие выбора, advice - добавляемое поведение, target - целевой объект, proxy - посредник. Spring AOP в типичном proxy-режиме перехватывает вызовы методов Spring-бинов, а не любую строку кода и не произвольный доступ к полю.

Before выполняется до вызова, after returning - после нормального возврата, after throwing - при исключении, after/finally - при завершении, around охватывает вызов и управляет proceed. Advice может изменить результат/исключение, поэтому порядок аспектов имеет значение.

## JDK proxy и class proxy

JDK proxy реализует интерфейсы. Class-based proxy наследует target-class; final-класс нельзя так расширить, final/private методы нельзя переопределить для перехвата. Точная доступность непубличных методов зависит от механизма и версии; для публичного прикладного контракта безопаснее явно использовать public-методы и внешний вызов через бин.

Конкретный выбор прокси зависит от настройки фреймворка/Boot; наличие интерфейса само по себе не доказывает, что именно JDK proxy применён в данном приложении. Определяйте фактический тип через диагностические средства, не через догадку.

## Self-invocation

```java
@Service
class Billing {
    void outer() { inner(); }
    @Transactional
    public void inner() { /* writes */ }
}
```

Если outer вызывает inner на том же `this`, вызов не проходит снова через обычный Spring AOP proxy. Аннотация inner поэтому не создаст новую транзакционную семантику сама по себе. Если outer уже вызван в активной транзакции, inner всё равно выполняется внутри неё; неверно говорить, что «при self-invocation транзакции никогда нет».

Решения: вынести операцию в отдельный бин с осмысленной ответственностью; вызвать TransactionTemplate; в специальных случаях использовать weaving AspectJ с другой моделью. Получение собственного прокси через AopContext увеличивает связанность и требует настройки.

Эта ловушка относится также к cache и async в обычном proxy-режиме. Объект, созданный вручную new, не получает Spring AOP только из-за аннотации. Схема и ограничения: [Proxying Mechanisms](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html).

## Как объяснить транзакционный interceptor

Посредник перед вызовом определяет атрибуты транзакции, через менеджер создаёт/присоединяет ресурс, вызывает target, затем commit либо rollback по правилам. Исключение должно пересечь нужную границу interceptor, если именно оно определяет откат. Aspect не заменяет SQL-lock и не контролирует внешнюю систему без отдельного протокола.

# 17. Spring Boot, конфигурация и сборка

## Что даёт Boot

Boot уменьшает ручную конфигурацию для типичных приложений: starters, dependency management, auto-configuration, executable archive, встроенный web-server, Actuator и тестовая поддержка. Starter - согласованный набор зависимостей; он не является отдельным сервером и не обязан сам содержать всю реализацию.

`@SpringBootApplication` объединяет Boot configuration, component scan и enable auto-configuration. Автоконфигурации применяются по условиям: доступен класс, есть/нет бин, задано свойство, выбран web-тип. Пользовательский бин часто заставляет конкретную автоконфигурацию отступить, но это определяется её условиями. Подключённый jar не доказывает, что все связанные бины реально созданы.

Condition evaluation report при debug помогает понять, почему конфигурация включилась. Можно исключить определённую auto-configuration. Не лечите каждую проблему исключением всего DataSourceAutoConfiguration, если приложение действительно требует БД. Основа: [Boot Auto-configuration](https://docs.spring.io/spring-boot/reference/using/auto-configuration.html).

## Конфигурация извне

Properties/YAML, environment, JVM system properties, arguments и другие источники объединяются с определённым приоритетом. Для обычного запуска arguments имеют приоритет над system properties и environment, а те - над стандартными config data; полный порядок включает тестовые и специальные источники. Не учите сокращённую схему как универсальную таблицу всех режимов.

`@Value` удобен для отдельного значения, `@ConfigurationProperties` - для связанной типизированной группы, в том числе Duration и коллекций. Используйте валидацию настроек и fail-fast при отсутствии обязательного секрета. Relaxed binding связывает, например, environment-форму с property-именем по правилам Boot.

Profiles переключают наборы настроек/бинов. Они не являются хранилищем секретов и не гарантируют правильное окружение автоматически. `application-prod.properties` может дополнять/переопределять общие свойства. `spring.config.import` подключает внешние config sources по правилам Config Data.

В проекте пароль БД и JWT-secret передаются через environment, `ddl-auto=validate`, Open Session in View отключён, Flyway включён. Файл `.env` Docker Compose и environment процесса Spring - разные уровни; переменная должна попасть в контейнер/процесс явно. Подробнее: [Externalized Configuration](https://docs.spring.io/spring-boot/reference/features/external-config.html).

## Gradle, BOM и артефакты

Gradle wrapper фиксирует версию инструмента. Toolchain задаёт JDK для задач, но не устанавливает автоматически любой произвольный runtime на машине пользователя. Version catalog в `gradle/libs.versions.toml` даёт aliases и явные версии. Dependency management/BOM согласовывает управляемые версии библиотек; явно зафиксированная версия может изменить итоговое разрешение, поэтому смотрите dependencyInsight.

`implementation` скрывает зависимость от компиляционного API потребителей модуля, `api` экспортирует её, `compileOnly` нужна при компиляции, `runtimeOnly` - при выполнении. Test-зависимости отделены. Это не уровни доступа Java, а конфигурации графа сборки.

`bootJar` упаковывает Boot-приложение с загрузчиком и зависимостями; обычный jar обычно не содержит их все. Shadow jar объединяет классы/ресурсы в другой формат fat jar, используемый отдельными модулями. Не запускайте всё как один произвольный jar без указания правильной задачи.

```bash
./gradlew :cps-backend:bootJar
./gradlew :cps-core:test :cps-backend:test
./gradlew :cps-backend:dependencies
java -jar cps-backend/build/libs/cps-backend.jar
```

Это команды для подготовки/демонстрации, а не отчёт об их выполнении в ходе написания пособия. Для запуска нужны согласованные БД и environment. Во встроенной модели web-server запускается приложением; WAR и внешний servlet container - другая схема размещения.

## Boot 4 и старые учебники

Проект использует Boot 4.1.2: starters и package names могут отличаться от учебников Boot 2/3. В коде уже есть `spring-boot-starter-webmvc`, `org.springframework.boot.persistence.autoconfigure.EntityScan`, модульные test-imports и Jackson 3 `tools.jackson`. Не переносите старый import механически. Jakarta-API используют `jakarta.*`, однако JDK-пакеты вроде `javax.crypto` не переименовывались по этому правилу.

# 18. Spring MVC, HTTP и REST

## Путь запроса

Клиент отправляет HTTP. Servlet container формирует request/response и запускает filters. Spring Security может завершить обработку до MVC. DispatcherServlet выбирает HandlerMapping и HandlerAdapter, разрешает аргументы метода, запускает binding/validation, вызывает controller, затем HttpMessageConverter сериализует ответ. HandlerExceptionResolver участвует в превращении ошибок в HTTP-ответ.

```text
HTTP -> Servlet filters / SecurityFilterChain -> DispatcherServlet
     -> handler mapping -> arguments / JSON / validation
     -> controller -> service -> repository -> database
     -> DTO -> message converter -> HTTP response
```

Filter работает на servlet-уровне; HandlerInterceptor - вокруг MVC handler; AOP охватывает методы бинов. Это разные точки расширения. Async dispatch добавляет особенности повторных проходов; нельзя предполагать ровно один вызов любого filter на все виды обработки. Модель: [DispatcherServlet](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html).

## Аннотации HTTP

`@RequestMapping` задаёт путь/условия, `@GetMapping` и аналоги сокращают mapping по методу. `@PathVariable` получает часть пути, `@RequestParam` - параметр запроса, `@RequestBody` - десериализованное тело, `@ModelAttribute` - связанные параметры объекта, `@RequestHeader` - заголовок. UUID в path проходит conversion; неверный формат - ошибка клиента, а не отсутствие сущности.

`@Controller` может возвращать имя view. `@RestController` эквивалентен Controller с ResponseBody-семантикой. `ResponseEntity` позволяет управлять статусом, headers и body. Content-Type описывает отправляемое представление; Accept - желаемые форматы ответа. Неподдерживаемое тело может дать 415, невозможное представление - 406.

## HTTP-методы и статусы

| Элемент | Смысл |
| --- | --- |
| GET / HEAD | Чтение; safe и idempotent по семантике. GET не должен менять бизнес-состояние. HEAD возвращает метаданные без тела. |
| POST | Обработка/создание под ресурсом. Идемпотентность не обещана; для повторов можно спроектировать idempotency key. |
| PUT | Создание/замена состояния по известному URI по контракту; идемпотентен. |
| PATCH | Частичное изменение по выбранному формату; идемпотентность зависит от операции. |
| DELETE | Удаление связи с ресурсом; идемпотентность эффекта не требует одинакового статуса каждого повтора. |
| 200 / 201 / 204 | Успех с телом; создание, часто с Location; успех без тела. |
| 400 / 401 / 403 / 404 | Неверный запрос; нет подходящей аутентификации; запрет; ресурс не найден/скрыт по политике. |
| 409 / 429 / 500 / 503 | Конфликт состояния; превышение лимита; внутренняя ошибка; временная недоступность. |

REST - архитектурные ограничения: ресурсы и представления, единый интерфейс, клиент-сервер, stateless-взаимодействие, кэширование, слои; hypermedia - часть строгого uniform interface. «JSON по HTTP» ещё не доказывает выполнение всех REST-ограничений. Для защиты достаточно честно описать используемый REST-style API.

## Контракт и DTO

Не отдавайте ORM entity автоматически: это связывает API с БД, может раскрыть поля, дать lazy-загрузки и циклы. Record DTO задаёт явные разрешённые данные. Не доверяйте присланным role, userId, цене и status только потому, что они прошли синтаксическую валидацию: требуется правило авторизации и предметной области.

PATCH должен различать «поле отсутствует», «поле равно null» и «задано значение», если контракт обещает очистку. В OrdersController null для notes сохраняет прежнее значение: текущий контракт не позволяет таким null очистить поле. Это следует объяснить, а не автоматически приписывать поддержку JSON Merge Patch.

Пагинация ограничивает нагрузку; сортировка идёт по allowlist и дополняется id. ETag/If-Match могут защищать от stale HTTP updates, но требуют явной реализации связи с версией и кодом 412. Наличие `@Version` само по себе не добавляет HTTP conditional requests.

# 19. Валидация и ошибки API

## Разные уровни проверки

Binding проверяет возможность разобрать JSON/UUID/дату. Bean Validation проверяет constraints DTO. Domain validation сохраняет бизнес-инварианты независимо от интерфейса. БД обеспечивает окончательную целостность. Авторизация отвечает, разрешено ли субъекту действие над конкретным объектом. Ни один уровень не заменяет все остальные.

`@NotNull` запрещает null; `@NotEmpty` также пустую строку/коллекцию; `@NotBlank` требует непробельный текст. `@Size` проверяет размер, не числовую величину. `@Positive` требует > 0, `@PositiveOrZero` допускает 0. Многие constraints считают null допустимым, поэтому отдельный NotNull часто необходим. DecimalMin/Digits задают ограничения десятичных чисел.

## @Valid и @Validated

`@Valid` запускает/обозначает каскадную проверку в поддерживающей инфраструктуре, например аргумента RequestBody и вложенных объектов. Для элементов коллекций нужны соответствующие type-use/cascade constraints. `@Validated` добавляет группы и используется в method validation Spring. Наличие аннотации в произвольном new-объекте не вызывает автоматическую проверку.

```java
public record OrderInput(
    @NotNull UUID userId,
    @NotEmpty List<@Valid LineInput> lines
) {}
public record LineInput(
    @NotNull UUID productId,
    @Positive int quantity
) {}
```

Для `createdFrom <= createdBefore` нужен межполевой constraint или явная проверка. Уникальность username нельзя гарантировать предварительным exists: между проверкой и записью возможна гонка, поэтому нужен UNIQUE и корректный ответ на конфликт.

Современный Spring MVC различает проверку отдельного аргумента и метода; могут возникать разные exception-типы. Не перехватывайте только MethodArgumentNotValidException и не считайте все остальные ошибки «неизвестными 500». Подробности: [MVC Validation](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-validation.html).

## Единая обработка

`@ExceptionHandler` связывает тип ошибки с ответом, `@RestControllerAdvice` распространяет политику на контроллеры. ProblemDetail задаёт стандартную основу error representation: type, title, status, detail, instance и расширения. Полезны field errors, стабильный error code и correlation id.

Не раскрывайте внутренний exception message автоматически: он может содержать SQL, имя таблицы, путь или секрет. Полный stack trace сохраняется в защищённом логе с id запроса; клиент получает понятное описание и подходящий status. Не логируйте одну ошибку многократно на каждом слое без необходимости.

Ошибки Security filter могут возникнуть до DispatcherServlet, поэтому ControllerAdvice не перехватывает их автоматически как обычное исключение controller. В проекте entry point и access denied handler явно делегируют в HandlerExceptionResolver. Это объясняет единый формат ответов на разных уровнях.

## Наблюдаемая несогласованность проекта

В `CreateProductRequest` цена отмечена `@Positive`, а core и SQL после V18 допускают неотрицательную цену. DTO также требует categoryId, тогда как Product допускает category=null. Это означает разные допустимые входы в разных интерфейсах. На защите называйте фактические контракты и возможное выравнивание правил, а не утверждайте, что все границы уже идентичны.

# 20. Spring Security и безопасность

## Authentication и authorization

Аутентификация устанавливает, кто обращается и каким доказательствам доверяет система. Авторизация решает, можно ли этому субъекту выполнить действие. SecurityContext содержит Authentication, principal и authorities. UserDetailsService загружает сведения об учётной записи; AuthenticationProvider проверяет поддерживаемый вид credentials, AuthenticationManager координирует providers.

DaoAuthenticationProvider использует UserDetailsService и PasswordEncoder для логина/пароля. При Bearer JWT другой путь: resource server извлекает токен, decoder проверяет подпись/claims, converter создаёт Authentication. JWT-путь не обязан повторять проверку пароля.

## Фильтры и цепочки

DelegatingFilterProxy связывает servlet filter с Spring, FilterChainProxy выбирает SecurityFilterChain. При нескольких chain применяется первая подходящая по порядку, а не все цепочки последовательно. `securityMatcher` выбирает цепочку; `requestMatchers` внутри определяет правила доступа. Method security через `@EnableMethodSecurity` и `@PreAuthorize` добавляет проверку на уровне вызова метода.

В проекте первая chain разрешает auth endpoints, Swagger и health; вторая защищает остальные запросы, закрывает прочие actuator paths и ограничивает admin по роли. `hasRole('ADMIN')` обычно проверяет authority с префиксом ROLE_. `@Order` здесь имеет конкретный смысл выбора chain. Модель: [Security Architecture](https://docs.spring.io/spring-security/reference/servlet/architecture.html).

## JWT

JWT обычно состоит из base64url header, payload и signature. Подпись обеспечивает проверку целостности и происхождения в выбранной модели ключей; содержимое обычного подписанного JWT не зашифровано. Base64 не защищает секреты. Проверяют допустимый algorithm, подпись, issuer, audience, exp, nbf при наличии и прикладное назначение.

HS256 использует общий секрет; любой держатель ключа может подписывать токены. В асимметричной схеме приватный ключ подписывает, публичный проверяет. Ключи должны иметь достаточную энтропию, храниться вне репозитория и поддерживать операционный процесс ротации. Не принимайте algorithm, предложенный недоверенным токеном, без политики.

Проект выдаёт HS256 access JWT со сроком по умолчанию 15 минут и refresh-сессию до 30 дней. JwtConfig проверяет issuer/audience/время/token_use. Converter дополнительно проверяет БД: активность sid, enabled пользователя и обязательную смену пароля; authority берётся из текущей учётной записи. Поэтому JWT здесь **не является полностью автономной проверкой без БД**. STATELESS относится к HTTP-session Spring Security, а не к отсутствию серверного состояния вообще.

Ресурсный сервер и сервер авторизации - разные роли. Наличие `oauth2ResourceServer().jwt()` не делает приложение полноценным OAuth2/OIDC authorization server. Подробности: [JWT Resource Server](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html).

## Пароли и refresh

Пароль хешируют адаптивным password hashing, а не обратимо шифруют и не хранят как обычный быстрый SHA-256. Salt предотвращает одинаковые хеши одинаковых паролей; work factor замедляет перебор. В проекте DelegatingPasswordEncoder использует bcrypt; учитывается ограничение длины bcrypt по байтам UTF-8. SHA-256 refresh-токена здесь имеет другой смысл: токен случайный и высокоэнтропийный, а не человеческий пароль.

Refresh-токен ротируется: старый помечается использованным, выдаётся новый. Повтор использованного токена отзывает сессию. `noRollbackFor=InvalidRefreshSessionException` нужен, чтобы сохранённый отзыв не отменился вместе с выдачей ошибки. Logout меняет серверное состояние сессии; последующая проверка access JWT видит отзыв через БД.

## CSRF, CORS и XSS

CSRF использует автоматически прикрепляемые браузером credentials. При Bearer только в Authorization header модель может обосновывать отключение CSRF, но «stateless значит CSRF невозможен» неверно: cookie-аутентификация сохраняет риск. При переносе refresh в cookie необходимо заново продумать CSRF, SameSite, Secure и HttpOnly.

CORS - браузерная политика междоменных запросов; она не заменяет аутентификацию и не защищает API от curl. Preflight OPTIONS требует согласованной настройки. XSS выполняет чужой JS в доверенном origin и может украсть доступные токены; выбор между browser storage и cookie имеет разные компромиссы. Основа: [Spring CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html).

## Проверка прав на объект

Роль USER не доказывает право на любой orderId. Нужна проверка владения/доступа для чтения и изменения конкретного заказа, защита от IDOR, а также контроль присланного userId. В текущем OrdersController общие операции не везде выражают владение: нельзя утверждать, что все USER видят только свои заказы. Ограничение редактирования собственных заказов есть в отдельных core-сценариях, но это не распространяется автоматически на все REST endpoints.

Rate limit снижает перебор и перегрузку, но локальная память лимитера не становится общим лимитом нескольких реплик. HTTPS защищает транспорт; JWT-подпись его не заменяет. Секреты, пароли и полные токены не должны попадать в access logs, error body и OpenAPI examples.

# 21. JPA и Hibernate: отображение модели

## Спецификация, провайдер и репозитории

Jakarta Persistence определяет контракт ORM: сущности, EntityManager, lifecycle, запросы и mapping. Hibernate реализует этот контракт и добавляет HQL, Session, soft delete и другие расширения. Spring Data JPA строит repository layer поверх EntityManager. JDBC остаётся нижележащим механизмом выполнения SQL в обычном стеке.

EntityManagerFactory - дорогая долгоживущая фабрика persistence units, EntityManager - единица работы. Hibernate SessionFactory/Session - близкие провайдерские понятия. Persistence unit объединяет конфигурацию и управляемые типы; persistence context хранит конкретные managed-экземпляры в рамках единицы работы.

## Требования к сущности

Entity имеет `@Entity` или XML mapping, первичный ключ и public/protected конструктор без параметров. В переносимой JPA-модели класс и нужные persistent members не должны нарушать требования к final/доступу; record не подходит как обычная entity. ORM нужен путь создания объекта без прикладного конструктора. Из-за этого инварианты должны поддерживаться не только одним публичным конструктором.

Положение `@Id` обычно задаёт field или property access. При field access ORM может читать/писать поля, не вызывая setter. Смешивание доступа без явного `@Access` создаёт неоднозначность. Static и Java transient поля не являются обычными persistent fields; `@Transient` явно исключает свойство из mapping.

## Базовые аннотации

```java
@Entity
@Table(name = "products")
class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;
    @Column(nullable = false, precision = 10, scale = 2)
    private BigDecimal price;
    @Version
    private Long version;
    protected Product() {}
}
```

`@Table` описывает таблицу; `@Column` - столбец, nullable, unique, precision/scale и mapping-ограничения. При ddl-auto=validate эти аннотации не создают новую production-схему автоматически. `updatable=false` исключает поле из обычного ORM UPDATE, но не запрещает прямой SQL и не является авторизацией.

`@Enumerated(STRING)` хранит имя enum; ORDINAL зависит от позиции. `@Convert` преобразует basic type через AttributeConverter. `@Embedded` встраивает value type, `@Embeddable` определяет его mapping. `@MappedSuperclass` передаёт mapping наследникам, но сам не является отдельной queryable entity.

## Идентификаторы

IDENTITY получает id из механизма БД при вставке и может осложнять batching insert. SEQUENCE использует sequence и допускает allocation; gaps нормальны и не означают потерю бизнес-записей. TABLE хранит генератор в таблице и может быть узким местом. UUID поддерживается Jakarta Persistence для подходящих идентификаторов; AUTO выбирает механизм по провайдеру/типу.

Id не обязан быть бизнес-номером без пропусков. Для юридически значимой последовательности проектируют отдельный процесс и требования. Составной ключ задают EmbeddedId или IdClass с корректным equals/hashCode; `@MapsId` связывает часть идентичности с отношением.

## Связи и owning side

ManyToOne и OneToOne - to-one; OneToMany и ManyToMany - to-many. JoinColumn обычно хранит FK, JoinTable задаёт таблицу соединения. В bidirectional-связи owning side управляет сохранением связи; `mappedBy` содержит **имя Java-поля связи**, а не имя SQL-колонки.

```java
// Владельцем связи является OrderItem.order.
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "order_id")
private Order order;

// Пример обратной стороны в другой учебной модели:
@OneToMany(mappedBy = "order")
private List<OrderItem> items = new ArrayList<>();
```

Учебный пример не описывает дословно текущую Order: в проекте позиции запрашиваются репозиторием отдельно. При двусторонней связи обновляйте обе стороны в памяти; в Product.addTag/removeTag это сделано для тегов. JPA не обязана сама синхронизировать обе Java-коллекции.

## Cascade, orphanRemoval и наследование

Cascade распространяет операции persistence, например PERSIST/MERGE/REMOVE, на связанные сущности. Он не равен SQL ON DELETE CASCADE. OrphanRemoval удаляет объект, исключённый из принадлежащей родителю связи по её контракту. Не ставьте CascadeType.ALL без анализа владения: REMOVE на общих товарах/тегах может уничтожить чужие данные.

Inheritance: SINGLE_TABLE хранит иерархию в одной таблице с discriminator, JOINED разделяет таблицы и требует joins, TABLE_PER_CLASS дублирует поля и усложняет полиморфные запросы. Выбор влияет на ограничения, чтение и миграции.

JPA callbacks `@PrePersist`, `@PreUpdate`, `@PostLoad` и entity listeners выполняются в определённых точках ORM lifecycle. Они не являются универсальным безопасным местом для произвольных запросов и внешних эффектов. В проекте аудит вынесен в listener и JDBC writer. Нормативная основа: [Jakarta Persistence 3.2](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2).

# 22. Persistence context и lifecycle entity

## Четыре состояния

| Состояние | Что означает |
| --- | --- |
| New / transient | Объект создан, но ещё не прикреплён к persistence context. |
| Managed / persistent | Контекст отслеживает объект и его persistent-состояние. |
| Detached | Объект имеет историю persistence, но больше не управляется данным контекстом. |
| Removed | Управляемый объект помечен на удаление при синхронизации. |

`persist` делает новую entity managed по правилам каскада. `find` получает управляемый экземпляр или null, используя контекст и БД по необходимости. `getReference` может вернуть ленивую ссылку и отложить обнаружение отсутствия. `detach` отсоединяет объект, `clear` - весь контекст, `refresh` перечитывает состояние из БД и может затереть локальные изменения.

## merge не прикрепляет исходный объект

```java
Product detached = loadEarlier();
Product managed = entityManager.merge(detached);
// Используем managed; detached сам не стал managed.
managed.setName("Updated");
```

Merge переносит состояние в managed-копию и возвращает её. Дальнейшая правка detached не обязана попасть в БД. Слепой merge DTO-подобного неполного объекта может затереть поля null/default и дать lost update. Для частичного обновления часто лучше загрузить managed entity и применить разрешённые поля.

## Dirty checking и flush

Контекст отслеживает изменения managed-сущностей. На flush Hibernate сравнивает состояние/использует механизм отслеживания и формирует SQL. Поэтому внутри корректной write-транзакции после изменения managed entity отдельный save не всегда технически нужен. Но сохранение через repository может оставаться частью принятого API; не добавляйте save ради мифа, что setter иначе никогда не работает.

Flush синхронизирует изменения с БД **внутри текущей транзакции**. Commit завершает транзакцию и делает её результат долговечным по контракту БД. Flush не равен commit и не гарантирует видимость другим транзакциям. SQL INSERT для некоторых стратегий id может выполняться раньше общего flush.

AUTO flush может происходить перед запросом, которому нужна согласованность, и при commit. Конкретное поведение native query зависит от API/провайдера. Ошибка constraint нередко появляется не на setter/save, а на flush/commit, то есть после возврата из тела target-метода, во время interceptor.

## Первый уровень кэша

В одном persistence context одному persistent identity соответствует один управляемый экземпляр соответствующей entity. Повторный find может вернуть его без нового SELECT, но JPQL-запрос сам по себе не обязательно устраняется. Первый уровень - не общий кэш приложения и не глобальный snapshot всех SQL-чтений.

После прямого SQL/bulk UPDATE контекст может содержать устаревшие entity. Flush перед таким запросом и clear/refresh после требуют осознанного порядка: clear до flush может потерять незаписанные изменения. Для больших batch-процессов периодические flush/clear ограничивают память и размер dirty checking.

## Lazy loading и OSIV

LAZY означает отложенную загрузку в доступных провайдеру рамках; для некоторых mapping это hint. EAGER требует доступности состояния, но не обещает один JOIN: ORM может выполнить дополнительные SELECT. По стандартным defaults to-one обычно EAGER, to-many LAZY. Всегда смотрите конкретный mapping и SQL.

Обращение к неинициализированной lazy-связи после закрытия Session может дать LazyInitializationException. Решение - загрузить нужные данные в сценарии и собрать DTO, применить fetch join/entity graph/projection. Делать все связи EAGER или включать OSIV ради сокрытия ошибки опасно: это может перенести SQL в сериализацию и создать N+1.

В проекте `spring.jpa.open-in-view=false`, ряд to-one связей EAGER выбран с учётом soft delete, а репозитории дополнительно используют fetch join/graphs. Это не отменяет анализа числа запросов. Отключение OSIV не отменяет транзакции и не запрещает все detached DTO.

# 23. Spring Data JPA и запросы

## Что создаётся по интерфейсу

Spring Data обнаруживает repository interfaces и создаёт прокси, который делегирует базовые CRUD-операции реализации и обрабатывает query methods/default methods/custom fragments. Это не генерация SQL исключительно по любому имени метода без правил. Repository должен быть зарегистрирован в подходящем контексте и связан с EntityManager.

Repository<T,ID> - маркерный базовый контракт; CrudRepository предоставляет CRUD, ListCrudRepository уточняет collection returns до List; JpaRepository добавляет JPA-операции вроде flush и batch-методов. Иерархии sorting/paging менялись между версиями: проверяйте фактические interfaces, а не старую схему наследования из презентации.

В проекте SpringProductsRepository использует ListCrudRepository и JpaSpecificationExecutor, а не JpaRepository напрямую. Поэтому нельзя приписывать ему любой метод JpaRepository без проверки наследования.

## save, find и delete

Save выбирает persist или merge по определению «новой» entity. По умолчанию учитывается nullable non-primitive version, затем id; возможен Persistable.isNew и другая настройка. Следовательно «id задан, значит объект точно обновляется» не является универсальным правилом. Всегда используйте возвращённый save объект, если важен managed-результат merge.

Save не означает немедленный commit. SaveAndFlush вызывает синхронизацию, но тоже не заменяет commit. FindById возвращает Optional, reference-операции могут отложить SELECT и ошибку отсутствия. Массовые delete/update могут отличаться от удаления загруженных entity по callbacks и состоянию контекста. Источник: [Persisting Entities](https://docs.spring.io/spring-data/jpa/reference/jpa/entity-persistence.html).

## Derived queries и @Query

```java
interface ProductRepo extends JpaRepository<Product, UUID> {
    List<Product> findByPriceGreaterThanOrderByNameAsc(
        BigDecimal min);

    @Query("select p from Product p where p.sku = :sku")
    Optional<Product> bySku(@Param("sku") String sku);
}
```

JPQL работает с entity names и Java-полями, SQL - с таблицами/колонками. HQL - язык Hibernate с дополнительными возможностями. Параметры связывают через имена или позиции; строковая конкатенация пользовательских значений в запрос опасна.

`@Query(nativeQuery=true)` позволяет SQL конкретной БД; mapping результата и pagination/count требуют проверки. Для UPDATE/DELETE в query method используется `@Modifying` и подходящая транзакция. Bulk DML обычно обходит обычный entity lifecycle и может оставить context устаревшим; clearAutomatically/flushAutomatically применяют осознанно. Query examples: [JPA Query Methods](https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html).

## Page, Slice, Sort и проекции

Page обычно содержит totalElements/totalPages и может потребовать отдельный COUNT. Slice показывает наличие следующего блока без обязательного общего count. List с Pageable может ограничить выдачу без всех metadata. Stream-результат требует управления ресурсом и подходящей транзакционной границы.

DTO projection выбирает только нужные поля; интерфейсные/конструкторные проекции имеют свои ограничения. `select new full.package.Dto(...)` использует подходящий конструктор. Проекция может избежать загрузки полного графа; она не гарантирует идеальный SQL для любого вложенного свойства.

## Specifications и Criteria API

Specification выражает predicate, из которого строится Criteria-запрос. Это удобно для набора опциональных фильтров и композиции AND/OR. CriteriaBuilder строит выражения, Root представляет entity, Join - связь. Динамичность не отменяет необходимости знать SQL и индексы.

В проекте фильтры поиска вынесены в отдельные модели, SearchPaging проверяет page/size и allowlist sort, затем добавляет уникальное поле сортировки. Если filter добавляет to-many join, возможны дубликаты, сложный count и необходимость distinct или подзапроса. Fetch-модификация одного запроса не всегда подходит count query.

Проверяйте границы диапазона, semantics null и способ escape LIKE. Передача `%` как значения безопасна от injection, но может менять смысл поиска; параметризация и экранирование wildcard - разные задачи. Подробнее: [Specifications](https://docs.spring.io/spring-data/jpa/reference/jpa/specifications.html).

## Транзакции репозитория

Базовые CRUD-операции имеют инфраструктурные transactional defaults, но declared query methods не следует считать автоматически охваченными всеми нужными атрибутами. Сценарная транзакция обычно задаётся на сервисе; при присоединении REQUIRED внешняя граница определяет физическую транзакцию. ReadOnly - подсказка/режим оптимизации, а не универсальное средство запрета SQL-записи. См. [Repository Transactionality](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html).

# 24. Производительность ORM и кэш

## N+1: как появляется

Один SELECT загружает N заказов, затем доступ к user каждого заказа запускает ещё N запросов. Получается 1+N обращений. EAGER способен создать ту же проблему через secondary selects. На маленьком H2-наборе задержка незаметна, а сеть до PostgreSQL умножает стоимость.

```text
Плохо: SELECT orders; затем SELECT user по каждой строке.
Цель: загрузить нужные связи/поля заранее подходящим запросом.
Проверка: число SQL, объём строк, время и план, а не вид кода.
```

Fetch join добавляет загрузку связи в запрос, entity graph задаёт нужный план, batch fetching группирует догрузки, DTO projection ограничивает поля. Ни один приём не решает все случаи. В проекте `SpringOrdersRepository.SELECT_QUERY` содержит JOIN FETCH user, а Product-выборки используют category graph/fetch.

## To-many fetch и пагинация

Join коллекции размножает строки родителя. Limit на SQL-строки не обязательно даёт правильную страницу родителей; провайдер может предупредить/перейти к pagination в памяти/запретить по настройке. Надёжный вариант - сначала получить страницу id, затем загрузить нужные данные по ним, сохранив порядок.

Одновременный fetch нескольких коллекций может дать декартово произведение и ограничения multiple bag fetching. Distinct не устраняет стоимость чтения огромного промежуточного набора. Count для страницы должен считать родителей с теми же фильтрами, а не случайно строки join.

## Кэш разных уровней

| Кэш | Что хранит и где |
| --- | --- |
| Persistence context | Managed entity в одной единице работы; первый уровень. |
| Hibernate second-level | Между contexts через настроенный provider и policy; не включается для всех entity одной аннотацией без инфраструктуры. |
| Query cache | Результаты запросов/идентификаторы по правилам провайдера; не то же, что entity cache. |
| Spring Cache | Результаты прикладных методов по ключу, поверх выбранного cache provider. |
| HTTP cache | Представления и validators по правилам HTTP. |

Кэш требует решения об invalidation, TTL, stale data, размере, ключах и tenant/user boundaries. Доступный товар и финансовые операции опасно защищать только кэшированным чтением. Кэш статистики может быть допустим при объявленной задержке обновления.

## Spring Cache

`@EnableCaching` подключает infrastructure; `@Cacheable` может вернуть существующий результат, `@CachePut` выполняет метод и обновляет запись, `@CacheEvict` удаляет. SpEL задаёт ключи и условия. Provider определяет хранение, TTL, распределённость и eviction; аннотация сама их не обеспечивает.

При обычном proxy-режиме внутренний вызов метода обходит cache interception. Ошибочный ключ может показать чужие данные. Очистку после записи согласуют с успешным commit, иначе кэш и БД могут расходиться. Подробнее: [Cache Annotations](https://docs.spring.io/spring-framework/reference/integration/cache/annotations.html).

## Запись и большие наборы

JDBC batching, размер batch и стратегия id влияют на число round trips. SaveAll не обещает один SQL-запрос и не равно batch INSERT само по себе. При импорте больших объёмов следите за памятью контекста, chunk size, порядком flush/clear и атомарностью всего файла либо части.

Не загружайте все заказы и позиции ради одного показателя, если агрегат может посчитать БД. Но SQL-оптимизация не должна нарушить soft-delete semantics и права. В проекте JdbcStatisticsRepository - пример прямой агрегатной проекции, а некоторые core-сервисы с getAll и stream-фильтром являются точкой возможного роста стоимости.

# 25. Транзакции в Spring

## ACID и граница сценария

Atomicity - всё или ничего в пределах транзакции; consistency - сохранение установленных инвариантов при корректных правилах; isolation - допустимое взаимодействие конкурентных транзакций; durability - сохранение подтверждённого результата по гарантиям СУБД. БД не угадывает бизнес-правило «менеджер не может повторно списать заказ»: его нужно выразить кодом/ограничениями.

Граница должна охватывать проверку и изменение связанного состояния. Если каждый repository save коммитится отдельно, ошибка на последнем шаге оставит частичный сценарий. Слишком длинная транзакция удерживает соединение/locks; не держите её во время долгого HTTP-вызова или ожидания пользователя без необходимости.

## Механизм Spring

PlatformTransactionManager абстрагирует begin/commit/rollback для ресурса; JpaTransactionManager обслуживает JPA, DataSourceTransactionManager/JdbcTransactionManager - JDBC, JTA - соответствующую распределённую модель. TransactionTemplate задаёт программную границу, `@Transactional` - декларативную через инфраструктуру перехвата.

`@Transactional` не создаёт самостоятельный DB engine и не обещает одинаковые возможности любого менеджера. В проекте template реализует Transactions.execute; вызовы блокирующих репозиториев с MANDATORY проверяют необходимость уже активной транзакции.

## Propagation

| Режим | Поведение |
| --- | --- |
| REQUIRED | Присоединиться к существующей или создать новую. Типичный default. |
| REQUIRES_NEW | Приостановить внешнюю и открыть независимую; нужен дополнительный ресурс/соединение. |
| SUPPORTS | Использовать текущую, если есть; иначе выполнять без неё. |
| MANDATORY | Требовать существующую; без неё ошибка. |
| NOT_SUPPORTED | Выполнять без транзакции, приостановив текущую при поддержке менеджера. |
| NEVER | Ошибка, если транзакция уже есть. |
| NESTED | Вложенная семантика обычно через savepoint; зависит от менеджера/драйвера и не равна REQUIRES_NEW. |

Логические REQUIRED-границы могут разделять одну физическую транзакцию. Если внутренняя помечена rollback-only, перехват ошибки снаружи не гарантирует успешный commit; может возникнуть UnexpectedRollbackException. REQUIRES_NEW может исчерпать пул при множестве внешних транзакций, удерживающих соединения. Подробнее: [Transaction Propagation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html).

## Rollback rules

Типичный default - rollback на RuntimeException и Error, а не на каждый checked exception. `rollbackFor`/`noRollbackFor` задают исключения из правила; современная конфигурация может менять общую политику. Не используйте абсолютное «checked никогда не откатывается». Ошибка, пойманная и скрытая внутри метода, может не пройти через interceptor; ресурс при этом уже способен быть rollback-only.

```java
@Transactional(rollbackFor = IOException.class)
public void importData() throws IOException {
    // Все согласованные изменения этого сценария.
}
```

ReadOnly сообщает намерение и позволяет оптимизации Hibernate/JDBC/СУБД, но степень запрета записи зависит от стека. Timeout относится к поддерживаемой транзакционной инфраструктуре и не является универсальным прерывателем любого кода. Isolation применяется при создании подходящей новой транзакции; вложенный REQUIRED не создаёт другой уровень физической транзакции автоматически.

## Events, async и внешние эффекты

Обычное событие Spring часто обрабатывается синхронно в вызывающем потоке. `@TransactionalEventListener` связывает реакцию с фазой транзакции, например AFTER_COMMIT. Это полезно, но отправка внешнего сообщения после commit может потеряться при падении процесса между commit и отправкой.

Outbox сохраняет бизнес-данные и запись сообщения в одной БД-транзакции; отдельный процесс доставляет её с повторами. Потребителю нужна идемпотентность. Обычная локальная транзакция не откатит уже отправленный email или внешний платёж. Для разных систем обсуждают XA/2PC или саги с компенсациями, понимая их стоимость.

Запуск `@Async` не переносит автоматически обычную thread-bound транзакцию вызывающего потока. Фоновый метод может открыть собственную, если вызван через соответствующую инфраструктуру. Аннотация не делает переданную managed entity безопасной для использования в другом потоке.

## Привязка к проекту

OrdersController имеет transactional-операции, а core дополнительно оборачивает сложные сценарии в Transactions. Сочетание REQUIRED обычно присоединяет их к одной транзакции. Для эволюции API можно перенести целые HTTP-сценарии в backend facade-service, сохранив контроллер транспортным. Это рекомендация, а не описание уже завершённого рефакторинга.

В RefreshSessionsService `noRollbackFor` сохраняет отзыв при replay refresh. В AuditEventWriter обычная запись MANDATORY должна откатываться вместе с бизнес-операцией; неуспешный login записывается REQUIRES_NEW. Настройка аннотаций: [Using @Transactional](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html).

# 26. Изоляция и конкурентные изменения

## Какие аномалии обсуждать

Dirty read читает неподтверждённые изменения. Non-repeatable read видит изменение одной строки между чтениями. Phantom связан с изменением набора строк по условию. Lost update теряет изменение при перезаписи старым состоянием. Write skew нарушает совместный инвариант через записи в разные строки. Эти явления нельзя свести к одному примеру count++.

| Уровень | Общая модель и оговорка |
| --- | --- |
| READ UNCOMMITTED | Стандарт допускает грязное чтение; PostgreSQL фактически трактует как READ COMMITTED. |
| READ COMMITTED | Нет dirty read; в PostgreSQL каждый statement видит свой снимок подтверждённых данных. |
| REPEATABLE READ | Повторяемость снимка транзакции по реализации; PostgreSQL сильнее минимальной стандартной защиты от phantom, но возможны serialization anomalies. |
| SERIALIZABLE | Эффект подтверждённых транзакций согласуется с последовательным выполнением; конфликты могут потребовать повторить всю транзакцию. |

MVCC хранит версии строк и даёт согласованное чтение без блокирования каждого читателя писателем. Это не означает отсутствие locks, конфликтов и служебного обслуживания vacuum. Семантика зависит от СУБД; для PostgreSQL см. [Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

## Optimistic locking

```sql
UPDATE products
SET price = ?, version = version + 1
WHERE id = ? AND version = ?;
```

`@Version` позволяет проверить, что строка не изменилась с момента чтения. Если ожидаемая строка не обновлена, возникает optimistic conflict. Это предотвращает многие lost updates конкретной entity. Повтор должен заново прочитать данные и применить намерение пользователя, а не бесконечно сохранять ту же старую копию.

Одна version товара не автоматически защищает агрегат всех заказов и остатков. Если два сценария вставляют разные строки без обновления общей version, возможен межстрочный конфликт бизнес-правила. Нужно выбрать общий объект блокировки/условный SQL/более строгую изоляцию.

## Pessimistic locking

PESSIMISTIC_WRITE обычно превращается в соответствующий механизм БД вроде SELECT FOR UPDATE. Точная форма SQL и блокирование связанных строк зависят от провайдера и БД. Lock удерживается до конца транзакции; запрос за пределами неё не обеспечивает нужной критической секции.

В `SpringProductsRepository.getByIdForUpdate` есть `@Lock(PESSIMISTIC_WRITE)` и `Propagation.MANDATORY`. OrderStock блокирует уникальные product ids в отсортированном порядке. Товар выступает общим координатором: после lock пересчитывается доступное количество. Это работает, если все пути изменения резерва/остатка следуют тому же протоколу.

## Пример двух покупателей

Физически есть 10 единиц, уже зарезервировано 0. А и Б хотят по 7. Без общей синхронизации оба читают 10 и создают резерв: всего 14. При общем lock товара А проверяет 10 и создаёт 7; Б ждёт, затем после завершения А пересчитывает доступность и видит 3, поэтому получает отказ. Существенно именно повторное чтение **после получения lock**, а не одна проверка в UI.

## Deadlock, retries и идемпотентность

Общий порядок product ids уменьшает deadlock между операциями с несколькими товарами, но не доказывает отсутствие deadlock во всех таблицах. Нужен единый порядок заказ/пользователь/сессия/товар и короткие транзакции. БД может выбрать жертву и откатить её.

Retry уместен для распознанных transient conflicts, с ограничением попыток и backoff. Повторяют всю атомарную операцию с новым чтением. Нельзя бездумно повторять side effects и неидемпотентный POST после сетевой ошибки: сервер мог уже подтвердить действие. Для важных команд проектируют idempotency key и уникальное хранение результата.

`synchronized` защищает только согласованный монитор внутри одного процесса и не заменяет DB locks при нескольких экземплярах приложения. Кэш и локальный Map также не координируют все реплики. Ограничения БД остаются последней общей защитой.

# 27. Flyway, soft delete и аудит

## Жизненный цикл схемы

Flyway применяет упорядоченные versioned migrations и ведёт schema history. Успешно применённую миграцию в общей БД обычно не переписывают: добавляют новую. Изменение checksum - сигнал несогласованности; repair не следует использовать как способ скрыть непонятную проблему.

Hibernate `ddl-auto=validate` проверяет соответствие mapping существующей схеме, а не проектирует production migrations. Create/create-drop подходит для некоторых изолированных тестов; update не заменяет контролируемые изменения структуры, индексов и данных. DDL-транзакционность зависит от СУБД и конкретных операций.

Expand/contract: сначала совместимое расширение схемы, затем код, перенос данных и только потом удаление старого. Добавление NOT NULL к большой заполненной таблице требует плана backfill и оценки блокировок. Резервная копия и проверенное восстановление важнее декларации «у нас есть миграции».

В проекте SQL лежит в `database/migrations`, Flyway включён, а ORM validate. V17 добавляет deleted_at и version, V18 согласует неотрицательность денег/остатков и уникальность пары product/warehouse, V19 касается soft delete связей тегов. Тест H2 с Flyway disabled не доказывает корректность этих миграций PostgreSQL.

## Soft delete

Мягкое удаление сохраняет строку и помечает её исключённой из обычной модели. В проекте `@SoftDelete(strategy=TIMESTAMP, columnName="deleted_at")` - расширение Hibernate, а не стандарт JPA. Прямой SQL и JdbcTemplate не получают ORM-фильтрацию автоматически: условия deleted_at должны быть заданы явно по смыслу запроса.

Soft delete влияет на unique constraints, ссылки, fetch-планы, восстановление и статистику. Архивная строка всё ещё может занимать уникальный sku. Если бизнес разрешает повторное использование, нужен продуманный partial unique index либо другая модель; это не возникает автоматически после добавления deleted_at.

Каскад мягкого удаления не следует предполагать по SQL FK: строка остаётся, поэтому ON DELETE не срабатывает как при физическом DELETE. В core удаление заказа явно обходит позиции и историю, затем заказ. Восстановление должно учитывать состояние родителей, уникальность и бизнес-правила. Административные обходы фильтра - отдельный контролируемый сценарий.

Ряд to-one связей в проекте EAGER с комментариями о soft delete. Это конкретное техническое решение провайдера/маппинга, а не общий принцип «все JPA-связи обязаны быть eager». Перед изменением нужно проверить ограничения используемого Hibernate и поведение отсутствующей/удалённой целевой строки. Руководство: [Hibernate ORM 7.4](https://docs.hibernate.org/orm/7.4/userguide/html_single/).

## Два вида аудита

История статусов хранит предметный факт oldStatus -> newStatus для заказа. Общий аудит фиксирует событие, объект, субъекта, время и correlation id. Обычный application log предназначен для диагностики; он не заменяет структурированный защищённый audit trail.

Spring Data auditing (`@CreatedDate`, `@LastModifiedDate`, `@CreatedBy`, AuditorAware) заполняет metadata при подключённой инфраструктуре. Hibernate Envers хранит revisions сущностей при отдельной настройке. В проекте используется собственный listener и AuditEventWriter, поэтому нельзя утверждать, что аудит реализован автоматически через Envers.

## Согласованность аудита

Backend подключает AuditEntityListener через orm.xml как persistence-unit default listener. Writer использует JdbcTemplate, чтобы не добавлять новые JPA actions внутри flush callback и не зациклить аудит самих audit entities. Обычная запись участвует в текущей транзакции; откат бизнес-операции должен убрать и её аудит изменений.

Неуспешная попытка логина - факт, который нужен даже без успешной бизнес-транзакции, поэтому для него выделен REQUIRES_NEW. При внешнем аудите нужны отдельные гарантии доставки. Доступ к журналу, редактирование/удаление, сроки хранения и исключение секретов должны соответствовать требованиям системы, а не определяться одной аннотацией.

# 28. Тестирование и доказательство корректности

## Уровни и назначение

Unit test проверяет локальное правило с контролируемыми зависимостями. Integration test проверяет взаимодействие настоящих компонентов: ORM/БД, context, security chain, HTTP binding. End-to-end охватывает пользовательский путь через более полный стек. Contract test проверяет договорённости интерфейсов. Наличие папки test не доказывает качество: важно, какой риск закрывает проверка.

JUnit Jupiter задаёт lifecycle и assertions: Test, BeforeEach, AfterEach, Nested, ParameterizedTest, assertThrows, assertAll. Arrange-Act-Assert помогает разделить подготовку, действие и наблюдение. Тест должен падать по осмысленной причине и не зависеть от порядка запуска.

Mock задаёт ожидаемое поведение зависимости и может проверять взаимодействие; stub просто возвращает подготовленные ответы; fake имеет упрощённую рабочую реализацию. Spy оборачивает реальный объект и требует осторожности с побочными эффектами. Не проверяйте только «метод save вызван»: важнее сохранённый бизнес-результат и откат при ошибке.

## Spring test tools

| Инструмент | Что проверяет |
| --- | --- |
| @SpringBootTest | Boot context целиком в выбранном webEnvironment; MOCK не обязательно поднимает настоящий network port. |
| @WebMvcTest | MVC slice с контроллерами и web-инфраструктурой; необходимые зависимости обычно подменяются/подключаются явно. |
| @DataJpaTest | JPA slice, mapping и repository behavior; настройки БД и rollback требуют понимания. |
| MockMvc | Servlet MVC request pipeline без реального socket exchange в типичном режиме. |
| WebTestClient | Проверка web endpoints с подходящим binding; часто используется в reactive stack и не ограничен только им. |
| Testcontainers | Реальная СУБД/сервис в контейнере для воспроизводимой интеграции; нужен доступный container runtime. |

Для замены бинов в современных Spring Test используется, в частности, `@MockitoBean`; старые Boot-примеры с `@MockBean` зависят от версии. В проекте Boot 4 test-imports уже модульные. Контекст может кешироваться между тестами; изменение общей mutable-зависимости влияет на соседей. DirtiesContext дорог и не должен заменять очистку собственных данных без причины.

Официальное руководство: [Testing Spring Boot Applications](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html).

## Что проверять в этой системе

- Создание заказа с несколькими позициями: весь сценарий сохраняется или целиком откатывается.
- Два конкурентных заказа на ограниченный остаток: суммарный резерв не превышает доступность.
- DELIVERED: списание ровно один раз, повторный запрос не списывает второй раз, обратный переход запрещён.
- Изменение/удаление позиции проверяет её принадлежность указанному заказу.
- Ошибочный JWT, истечение, неправильный issuer/audience, отключение пользователя, отзыв sid и replay refresh отклоняются.
- Роль и обязательная смена пароля реально ограничивают endpoints; отдельно проверяется доступ к чужому объекту по требованиям.
- Миграции применяются на пустой PostgreSQL и обновляют предыдущую схему; validate проходит после них.
- Soft delete исключает записи из обычного чтения, а статистика правильно различает active/archived.
- Валидация граничных значений, money precision, дубликатов sku и пары product/warehouse даёт согласованный контракт.

## H2 и PostgreSQL

H2 полезна для быстрых тестов, но отличается типами enum, SQL, временными значениями, индексами, locks и изоляцией. PostgreSQL compatibility mode не превращает H2 в PostgreSQL. В InfrastructureIntegrationTest и SecurityIntegrationTest проекта используется H2, schema create-drop и отключённый Flyway. Это доказывает часть поведения Java/Spring, а не всю production-семантику миграций и конкурентности.

Transactional test с автоматическим rollback может скрыть ошибку, которая возникла бы на commit. Вызывайте flush там, где проверяете constraint, и отдельно проверяйте реальную границу завершения транзакции. Для конкурентного теста нужны разные соединения/транзакции и управляемая синхронизация, а не один последовательный вызов два раза.

## Управляемое время и нестабильность

Fixed Clock делает тест JWT и сроков сессии детерминированным. Latch/barrier позволяет задать чередование потоков без случайного sleep. Каждый тест должен очищать своё состояние. Не используйте бесконечные ожидания, общую случайную БД и зависимость от местного часового пояса.

**Как отвечать преподавателю:** «Проверка X доказывает Y в окружении Z. Она не проверяет Q, для этого нужен отдельный интеграционный сценарий». Точный предел доказательства убедительнее утверждения «всё покрыто тестами».

# 29. Остальная экосистема Spring

Этот раздел расширяет кругозор для дополнительных вопросов. Перечисленные технологии не следует называть реализованными в проекте без отдельного кода и конфигурации.

## Async и scheduling

`@EnableAsync` и `@Async` позволяют передать выполнение в executor. Метод обычно возвращает void/Future/CompletableFuture по поддерживаемому контракту; ошибки требуют обработки. Ограничьте pool/queue, определите rejection policy и контекст трассировки. В proxy-режиме self-invocation не передаёт задачу executor.

`@EnableScheduling` подключает `@Scheduled`. FixedDelay измеряет задержку после завершения, FixedRate ориентирован на заданную частоту запуска; реальное пересечение зависит от scheduler/исполнителя. Cron имеет формат Spring и отдельное управление zone. Несколько реплик обычно запустят одну и ту же задачу каждая: для единственного выполнения нужны coordination/lock либо внешний scheduler.

В проекте очистка истёкших refresh-сессий использует Scheduled с configurable interval и transactional method. Наличие scheduler не гарантирует удаление строго в момент истечения; проверка активности сессии должна работать независимо. Подробнее: [Task Execution and Scheduling](https://docs.spring.io/spring-framework/reference/integration/scheduling.html).

## Events, resources и i18n

ApplicationEventPublisher публикует события, EventListener обрабатывает их; по умолчанию это не обязательная durable queue. Resource абстрагирует classpath/file/URL источник; classpath-ресурс внутри jar не обязательно доступен как обычный File. MessageSource хранит локализуемые сообщения, LocaleResolver/Context определяют язык. Часовой пояс и язык не следует смешивать.

SpEL вычисляет выражения в аннотациях/конфигурации, например в PreAuthorize и Cacheable. Не исполняйте выражения, пришедшие от недоверенного пользователя, с полномочиями приложения.

## MVC, WebFlux и Reactor

WebFlux - reactive web-stack с неблокирующей моделью и поддержкой Reactive Streams. Mono представляет 0/1 результат, Flux - 0..N. Pipeline обычно ленив, ошибки идут как сигналы; backpressure позволяет потребителю ограничивать спрос. Реактивная цепочка - не просто «метод в новом потоке».

Блокирующий JPA внутри event-loop способен остановить обработку других задач. Перенос на bounded scheduler может изолировать блокирование, но не делает драйвер неблокирующим. R2DBC - отдельная модель SQL-доступа без обычного JPA persistence context/dirty checking. Реактивная транзакция опирается на reactive context и подходящий manager, а не только на ThreadLocal.

MVC плюс virtual threads может быть разумен для блокирующей системы. Выбор зависит от workload, библиотек и навыков; WebFlux не гарантирует меньшую задержку при любой нагрузке. См. [WebFlux Overview](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html), [R2DBC](https://docs.spring.io/spring-framework/reference/data-access/r2dbc.html).

## Другие Spring Data

Spring Data JDBC использует агрегатную модель без полного JPA lifecycle и lazy dirty checking. Spring Data MongoDB работает с документной БД; MongoDB не становится реляционной из-за Repository API. Redis часто используют для кэша/координации с выбранными гарантиями; Elasticsearch - поисковый индекс. Одинаковое имя save не означает одинаковую семантику транзакций и согласованности во всех stores.

Query by Example удобен для шаблонных фильтров, Specifications/Criteria - для композиции условий в JPA, Querydsl - отдельный подход с типизированным query DSL. Выбор инструмента не отменяет анализ SQL и потребностей индексации.

## Messaging: Kafka, AMQP, JMS

Spring for Apache Kafka, Spring AMQP и JMS abstractions упрощают интеграцию с разными brokers. Сообщение может доставляться повторно; ack, retry, ordering, consumer groups, dead-letter и transaction boundaries зависят от технологии. «Exactly once» всегда имеет конкретную область гарантий и не делает произвольный внешний платёж ровно однократным.

Надёжная обработка требует идемпотентного consumer, ключа события, политики повторов и наблюдаемости. Outbox связывает запись в БД с будущей публикацией. Упорядоченность одной partition не означает глобального порядка всех событий.

## Batch и Integration

Spring Batch описывает Job, Step, JobExecution и метаданные выполнения; chunk processing использует reader/processor/writer и границы commit. Restart, retry и skip должны соответствовать предметным правилам. Пакетный импорт с возможностью продолжить после сбоя существенно сложнее цикла saveAll. Руководство: [Spring Batch](https://docs.spring.io/spring-batch/reference/index.html).

Spring Integration реализует enterprise integration patterns: channel, endpoint, transformer, router, splitter, aggregator и adapters. Это про потоки сообщений и связывание систем; не путайте с общим термином integration test. См. [Spring Integration Overview](https://docs.spring.io/spring-integration/reference/overview.html).

## Cloud, Modulith и resilience

Spring Cloud объединяет средства configuration, discovery, routing, load balancing и circuit breaker вокруг распределённых систем. Release train должен быть совместим с выбранным Boot. Timeout ограничивает ожидание, retry повторяет, circuit breaker временно отсекает проблемную зависимость, bulkhead изолирует ресурсы. Сочетание неконтролируемых retries на всех уровнях способно усилить аварию.

Микросервисы усложняют согласованность, наблюдаемость и развертывание. Spring Modulith помогает структурировать модульный монолит и взаимодействия модулей. Для учебной закупочной системы отдельные deployable services не обязательны. Проектные модули Gradle сами по себе не означают микросервисную архитектуру. Обзор: [Spring Cloud](https://spring.io/projects/spring-cloud/).

## Другие web-интерфейсы и AOT

WebSocket поддерживает двусторонний канал; SSE - поток событий сервера клиенту поверх HTTP. GraphQL задаёт схему и выбираемые поля, но требует контроля authorization, query complexity и N+1. SOAP/Web Services используют другой контрактный стек; REST не единственный способ интеграции.

Spring HATEOAS помогает строить hypermedia representations. Spring Session выносит HTTP-session в выбранное хранилище; он не тождественен таблице refresh_sessions проекта. LDAP/Vault/Authorization Server решают специализированные security-задачи.

AOT и native image могут улучшить запуск/потребление памяти, но меняют требования к reflection, resource discovery и динамике. Их нужно проверять на реальном приложении; одна native-настройка не гарантирует совместимость всех ORM/JavaFX библиотек. DevTools удобен в разработке, не является механизмом production-мониторинга.

# 30. Эксплуатация, Docker и наблюдаемость

## Как приложение работает вне IDE

Артефакт должен запускаться с известной Java, конфигурацией, доступной БД и миграциями. Docker image описывает среду процесса; container - её работающий экземпляр. Compose собирает несколько сервисов, network и volumes. Volume PostgreSQL сохраняет данные отдельно от жизненного цикла контейнера; его потеря не лечится пересозданием приложения.

В docker-compose.yml PostgreSQL и backend общаются по имени сервиса `postgres`; localhost внутри backend - сам backend, а не контейнер БД. Host port mapping нужен внешнему клиенту. Compose привязывает порты к 127.0.0.1, требует пароль БД/JWT secret через environment и задаёт healthchecks. Готовность БД не означает, что все бизнес-функции приложения уже исправны.

## Health, liveness и readiness

Liveness отвечает, способен ли процесс продолжать работу; readiness - можно ли направлять ему трафик. При падении общей БД перезапуск всех живых приложений может лишь ухудшить ситуацию; зависимости часто уместнее отражать в readiness. Конкретная политика определяется окружением.

Actuator предоставляет endpoints и интеграцию health/metrics. Доступность endpoint зависит от разрешённого access и exposure, а HTTP security определяет, кто может обратиться. В проекте открыт только aggregate health без подробностей, остальные actuator paths закрыты. Нельзя заявлять, что Prometheus или все метрики уже опубликованы. См. [Actuator Endpoints](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html).

## Logs, metrics, traces

Лог фиксирует событие с контекстом; метрика агрегирует измерение; trace связывает spans распределённой операции. Correlation id помогает найти записи одного запроса, но сам по себе не является полной распределённой трассировкой. MDC требует очистки и корректного переноса в async.

Полезны latency p50/p95/p99, error rate, throughput, saturation pool/queue, время SQL и число locks. Среднее время скрывает хвост задержек. Не используйте userId/token как неограниченные labels метрик: высокая cardinality раздувает хранилище. Включение подробного SQL в production требует оценки объёма и чувствительных значений.

## Надёжность и масштабирование

Горизонтальное масштабирование добавляет экземпляры, вертикальное - ресурсы одного. При нескольких backend согласуют rate limiting, scheduling, кэш и общий state. JWT не устраняет зависимость текущей реализации от БД сессий. Суммарное число соединений равно соединениям всех экземпляров, поэтому «по 50 на каждый» быстро перегружает PostgreSQL.

Задайте connection timeout, query timeout, границы request size, pagination и executor queues. Graceful shutdown прекращает приём нового трафика и даёт текущим операциям ограниченно завершиться. Повтор после сетевого сбоя должен учитывать неизвестность результата предыдущей попытки.

## Резервирование и изменения

Проверяйте не только создание backup, но и восстановление в согласованное состояние. Продумывайте migration rollout/rollback, совместимость API и данных. Rollback приложения не всегда откатывает схему или необратимую бизнес-операцию. Здоровый endpoint не является доказательством отсутствия потери данных.

Секреты не коммитятся; зависимости обновляются осознанно с проверкой совместимости и уязвимостей. Для воспроизводимости фиксируются версии и граф сборки. OpenAPI и Swagger UI документируют контракт, но аннотация Operation не реализует проверку доступа и не заменяет тест реального ответа.

## Проследить конкретный запрос

Для PATCH `/api/orders/{id}`: security chain проверяет Bearer, decoder проверяет JWT, converter читает sid/аккаунт, method security проверяет разрешение менять status. MVC связывает UUID и UpdateOrderRequest и валидирует тело. Controller начинает transactional-сценарий, при status вызывает orders.changeStatus с субъектом из JWT, а при notes вызывает updateOrder.

Core через Transactions присоединяет работу к общей транзакции; заказ читается с write lock. Проверяется роль менеджера/администратора. При повторе того же статуса changeStatus возвращается. При DELIVERED OrderStock проверяет и списывает товар; история сохраняет старый и новый статус. Репозитории выполняют JPA/JDBC-операции, ORM flush и commit завершают изменения, search строит OrderResponse.

Важная оговорка: `@PreAuthorize` и проверка роли не доказывают владение заказом для всех операций. Не следует приписывать endpoint скрытые ограничения, которых нет в коде.

# 32. Справочник аннотаций

В каждой строке важно знать не только название, но и обработчик. Импорт определяет семейство аннотации; одинаковые простые имена могут иметь разный смысл.

| Группа | Назначение и ловушка |
| --- | --- |
| @Override, @Deprecated, @SuppressWarnings | Проверка override, устаревание API, подавление compiler warnings. SuppressWarnings не исправляет причину проблемы. |
| @Retention, @Target, @Inherited | Жизнь и область применения metadata; Inherited не означает наследование любых методов. |
| @Component / @Service / @Repository | Стереотипы бинов; Repository имеет смысл для persistence exception translation при настройке. |
| @Configuration / @Bean / @Import | Явная сборка context. Учитывайте proxyBeanMethods. |
| @Autowired / @Qualifier / @Primary | Injection и выбор кандидата; один constructor часто не нуждается в Autowired. |
| @Scope / @Lazy / @DependsOn | Область экземпляра, отложенное разрешение/создание, зависимость инициализации. |
| @PostConstruct / @PreDestroy | Init/destroy lifecycle через контейнер, не на произвольном new. |
| @SpringBootApplication | Boot configuration, scan, auto-configuration. Не находит автоматически все пакеты проекта. |
| @ConfigurationProperties / @Profile | Типизированные настройки и условия активации; не хранилище секретов. |
| @EntityScan / @EnableJpaRepositories | Настройка поиска entity и repository; ComponentScan - отдельная область. |
| @RestController / @RequestMapping | HTTP handler и маршрутизация. Не реализуют бизнес-права автоматически. |
| @RequestBody / @RequestParam / @PathVariable | JSON body, query parameter, сегмент пути; conversion имеет собственные ошибки. |
| @ModelAttribute / @RequestHeader | Связывание полей формы/query; значение заголовка. |
| @ResponseStatus / @ExceptionHandler | Статус и локальная обработка исключений; могут быть перекрыты другой логикой ответа. |
| @RestControllerAdvice | Общая MVC-политика ответов/ошибок, не автоматический перехват всех filters. |
| @Valid / @Validated | Cascade validation и группы/method infrastructure; нужен активный механизм проверки. |
| @NotNull / @NotBlank / @Size | Наличие, непробельный текст, длина/размер; не взаимозаменяемы. |
| @Positive / @Digits / @DecimalMin | Числовые constraints; многие допускают null отдельно от NotNull. |
| @Transactional | Interceptor + transaction manager; учитывайте self-invocation, rollback и propagation. |
| @EnableMethodSecurity / @PreAuthorize | Разрешение method checks и predicate доступа; нужен вызов через инфраструктуру. |
| @AuthenticationPrincipal | Получение principal текущей аутентификации, не самостоятельная проверка владения объектом. |
| @Entity / @Table / @Column | ORM entity, таблица, колонка; не делают класс обычным Spring-service. |
| @Id / @GeneratedValue / @Version | Идентичность, генерация ключа, optimistic version control. |
| @ManyToOne / @OneToMany / @JoinColumn | Cardinality и FK mapping; fetch и cascade - отдельные настройки. |
| @ManyToMany / @JoinTable | Связь через таблицу соединения; owning side управляет записью связи. |
| @Enumerated / @Embedded / @Convert | Enum representation, встроенное значение, basic conversion. |
| @PrePersist / @PreUpdate / @EntityListeners | ORM lifecycle; bulk SQL обычно не вызывает entity callbacks как поштучная работа. |
| @SoftDelete / @CreationTimestamp | Hibernate extensions; переносимость и точная семантика зависят от провайдера. |
| @Query / @Param / @Modifying | Явный repository query, binding, DML; нужна подходящая транзакция. |
| @EntityGraph / @Lock | План загрузки и lock mode; не гарантируют идеальную производительность сами по себе. |
| @EnableCaching / @Cacheable / @CacheEvict | Кэш прикладных результатов; provider/ключ/TTL определяются отдельно. |
| @EnableAsync / @Async | Передача задачи executor; не автоматическое наследование транзакции. |
| @EnableScheduling / @Scheduled | Периодический запуск; несколько реплик могут выполнять задачу каждая. |
| @EventListener / @TransactionalEventListener | События context и привязка к фазе транзакции; не durable broker. |
| @Test / @ParameterizedTest | JUnit-исполнение обычных/параметризованных тестов. |
| @SpringBootTest / @WebMvcTest / @DataJpaTest | Полный context и test slices с разными пределами доказательства. |
| @WithMockUser | Тестовая аутентификация; не доказывает правильность подписи/decoder настоящего JWT. |
| @Operation / @ApiResponse | Документирование OpenAPI; не реализует заявленное поведение. |

**Устная формула:** «Эту аннотацию обрабатывает X на этапе Y. Для неё нужен Z. Она даёт A, но сама по себе не обеспечивает B». Например, EntityGraph обрабатывается JPA-инфраструктурой при выполнении запроса, задаёт план загрузки и не заменяет проверку SQL-count.

# 33. Вопросы 1-50: Java и проектирование

Отвечайте сначала самостоятельно. Ответы здесь - опорные формулировки; определения, механизмы и примеры подробно раскрыты выше.

**1. Чем JDK отличается от JVM?** JVM выполняет bytecode, JDK даёт инструменты разработки и runtime. Javac относится к JDK; переносимость требует совместимой среды и зависимостей.

**2. Почему Java называют платформонезависимой?** Компиляция создаёт bytecode для совместимой JVM. Нативные библиотеки, OS-specific пути и версия class-файла могут ограничивать запуск.

**3. Java передаёт объекты по ссылке?** Аргументы всегда передаются по значению. Для объекта копируется ссылка: общий объект можно изменить, но переприсваивание параметра не заменяет переменную вызывающего кода.

**4. Что даёт final у ссылки?** Запрещает присвоить другую ссылку после инициализации. Изменяемое состояние объекта остаётся доступно, если его API это разрешает.

**5. Что означает static?** Принадлежность члену класса, а не конкретному экземпляру. Static-метод не использует this и не участвует в обычном instance override.

**6. Overload и override - в чём разница?** Overload выбирает сигнатуру при компиляции, override - реализацию экземплярного метода по runtime-типу. Возвращаемого типа недостаточно для перегрузки.

**7. Можно ли переопределить private или final метод?** Final запрещает override; private не наследуется как переопределяемый контракт. Одноимённый метод наследника не делает private-метод полиморфным.

**8. Зачем конструктор без аргументов у entity?** ORM нужен предусмотренный контрактом способ создать экземпляр. Наличие другого конструктора не заставляет компилятор добавить no-args автоматически.

**9. Чем интерфейс отличается от abstract class?** Интерфейс задаёт контракт и допускает множественную реализацию; abstract class может хранить экземплярное состояние и иметь конструктор. Класс наследует только один superclass.

**10. Почему композиция часто удобнее наследования?** Позволяет менять сотрудничающий алгоритм через dependency без жёсткой иерархии. Наследование уместно, когда подтип сохраняет контракт базового типа.

**11. В чём реальная инкапсуляция?** В контроле допустимых изменений состояния. Private-поле с getter, выдающим внутренний mutable List, всё ещё может позволять обходить правила.

**12. Что такое LSP на примере repository?** Любая реализация должна сохранять ожидания клиента: getById не удаляет запись и корректно представляет отсутствие. Более жёсткие скрытые предусловия ломают подстановку.

**13. DI и DIP - одно и то же?** DIP определяет направление зависимостей от абстракций, DI передаёт зависимости объекту. DI можно реализовать вручную без Spring.

**14. Какие правила обязаны соблюдать equals и hashCode?** Равенство должно иметь свойства эквивалентности и согласованный hash. Равные объекты имеют одинаковый hash; одинаковый hash не доказывает equals.

**15. Почему mutable key в HashMap опасен?** Изменение полей, влияющих на equals/hashCode, меняет способ поиска ключа после помещения в bucket. Запись может перестать находиться ожидаемым get.

**16. Чем == отличается от equals?** Для примитивов сравнивает значения по правилам языка, для ссылок - идентичность. Equals задаёт логическое равенство и может быть переопределён.

**17. Почему Integer через == иногда «работает»?** Некоторые значения wrappers кешируются. Это деталь идентичности и не основание сравнивать wrapper-значения через ==.

**18. Что произойдёт при unboxing null?** NullPointerException. Nullable Integer следует проверять или явно выбирать default до преобразования в int.

**19. String immutable, значит любые операции над строками thread-safe?** Состояние String неизменяемо, но составная логика и переменная-ссылка могут иметь гонки. Иммутабельность одного объекта не синхронизирует весь алгоритм.

**20. Чем StringBuilder отличается от String?** Builder изменяем и удобен для накопления текста. Для совместного изменения из разных потоков он требует внешней координации.

**21. Почему double не подходит для цены?** Двоичное floating-point представление не даёт точного десятичного значения для многих сумм. BigDecimal с определённым scale/rounding лучше выражает денежные правила.

**22. Равны ли BigDecimal 1.0 и 1.00?** CompareTo считает численно равными, equals учитывает scale и может вернуть false. Это важно для Set, Map и тестов.

**23. Instant и LocalDateTime - одно и то же?** Instant задаёт момент, LocalDateTime не содержит зоны/смещения. Для преобразования LocalDateTime в момент нужна дополнительная договорённость.

**24. Зачем внедрять Clock?** Чтобы управлять временем в тестах и не зависеть от текущих часов/зоны машины. Это особенно важно для exp JWT и срока сессий.

**25. Что выбрать: ArrayList или LinkedList?** Обычно по реальному workload; ArrayList даёт быстрый индексный доступ и хорошую locality. LinkedList не делает поиск и вставку по произвольному индексу O(1).

**26. Чем HashSet отличается от TreeSet?** HashSet использует hash/equals, TreeSet - порядок сравнения. Если Comparator считает разные по equals объекты одинаковыми, поведение уникальности будет различаться.

**27. HashMap - всегда O(1)?** Это ожидаемая стоимость при подходящем распределении, а не универсальная гарантия всех условий. Размер, коллизии, распределение и реализация влияют на результат.

**28. Можно ли безопасно менять HashMap из двух потоков?** Без подходящей синхронизации - нет. ConcurrentHashMap решает часть задач, но составной check-then-act тоже должен быть атомарным по смыслу.

**29. Чем List.of отличается от unmodifiableList?** List.of создаёт структурно неизменяемую коллекцию без null. UnmodifiableList может быть view на изменяемый исходный список; элементы в обоих случаях не замораживаются автоматически.

**30. Почему List<Integer> не List<Number>?** Generics инвариантны: иначе в Integer-список через Number-ссылку можно было бы добавить Double. Для чтения используют подходящий wildcard.

**31. Объясните PECS.** Producer extends удобен для чтения T; consumer super позволяет добавлять T. Список неизвестного верхнего подтипа нельзя безопасно наполнить произвольным T.

**32. Что стирается при type erasure?** Многие runtime-представления generic-параметров. Некоторые декларативные signatures остаются metadata; стирание не означает полное исчезновение всей generic-информации из class-файла.

**33. Чем checked exception отличается от unchecked?** Checked требует catch/throws при компиляции, RuntimeException - нет. Это не шкала серьёзности и не универсальное правило rollback.

**34. Что делает try-with-resources?** Закрывает AutoCloseable ресурсы в обратном порядке. При основной ошибке ошибка close может оказаться suppressed, сохраняя первичную причину.

**35. Можно ли вернуть значение из finally?** Можно, но это способно подавить исходное исключение/return. Такой код обычно скрывает ошибку и затрудняет понимание.

**36. Зачем хранить cause исключения?** Для диагностики первичной причины, SQLState и цепочки ошибок. Клиенту можно дать безопасное сообщение, не теряя внутреннюю причину в логах.

**37. Когда запускается Stream pipeline?** При terminal operation. Промежуточные операции обычно ленивы, а повторно использовать один уже потреблённый stream нельзя.

**38. Map и flatMap?** Map возвращает по одному преобразованному результату на элемент; flatMap разворачивает полученные последовательности/контейнеры в плоскую структуру.

**39. Почему parallelStream опасен рядом с JPA?** Операции могут выполняться в других потоках без нужного transactional context, а Session не thread-safe. Побочные эффекты и blocking I/O дополнительно усложняют исполнение.

**40. Чем orElse отличается от orElseGet?** Выражение аргумента orElse вычисляется заранее. Supplier в orElseGet вызывается только при пустом Optional.

**41. Что такое функциональный интерфейс?** Интерфейс с одним абстрактным методом по правилам языка. Lambda и method reference реализуют его контракт.

**42. Делает ли record объект полностью immutable?** Нет, компоненты final, но вложенные mutable-объекты могут изменяться. Для списка нужна копия и контроль самих элементов по требованиям.

**43. Что делает аннотация без обработчика?** Только хранит metadata в пределах retention. Собственная аннотация не запускает аудит/валидацию автоматически.

**44. SOURCE, CLASS и RUNTIME?** Уровни сохранения аннотации: исходный код, class-файл и runtime reflection соответственно. Retention по умолчанию - CLASS.

**45. @Inherited работает на методы интерфейса?** Не как универсальное правило Java-аннотаций. Она относится к наследованию аннотации класса; Spring может иметь собственный более широкий механизм поиска metadata.

**46. Что собирает GC?** Недостижимые объекты, а не просто объекты с нулём ссылок между собой. Изолированный цикл без пути от roots тоже может быть собран.

**47. Возможна ли утечка памяти в Java?** Да, достижимые, но ненужные объекты могут удерживаться static-коллекциями, listeners, ThreadLocal и кэшем. GC не знает, что бизнес-коду они больше не нужны.

**48. Volatile делает increment атомарным?** Нет. Оно даёт гарантии видимости/порядка, но count++ остаётся составной операцией; нужен atomic primitive или lock по инварианту.

**49. Virtual threads ускорят вычисление отчёта на CPU?** Сами по себе нет. Они помогают масштабировать ожидающие I/O задачи; CPU, БД и число connections остаются ограниченными.

**50. Всегда ли main обязан быть public static?** Для классических версий используется такая форма. В целевой Java 25 допустимы расширенные main-формы, поэтому нужно учитывать версию, а не механически применять старое правило.

# 34. Вопросы 51-100: Spring, Boot, MVC, Security

**51. Что такое IoC?** Передача части управления жизненным циклом/вызовами фреймворку. DI - конкретный способ предоставления зависимостей в этой модели.

**52. Что является Spring-бином?** Объект, которым управляет контейнер в соответствии с зарегистрированным определением/экземпляром. Аннотация на классе без регистрации не превращает каждый new в бин.

**53. BeanFactory и ApplicationContext?** Первый даёт базовое управление бинами, второй расширяет его событиями, ресурсами, сообщениями и контекстной инфраструктурой. Boot обычно работает с ApplicationContext.

**54. Почему constructor injection предпочтителен?** Обязательные зависимости видны в API объекта, допускают final и простое unit-тестирование. Это не запрещает setter для настоящих optional-зависимостей.

**55. Что будет при двух реализациях одного интерфейса?** Без правила выбора возможна неоднозначность. Используют Qualifier/Primary или получают коллекцию всех реализаций по нужному контракту.

**56. @Primary и @Order взаимозаменяемы?** Нет. Primary помогает выбрать кандидата, Order задаёт порядок в поддерживающей инфраструктуре, например цепочках или упорядоченных наборах.

**57. Singleton означает один объект в JVM?** Нет, область связана с bean definition и контейнером. Два контекста или два определения могут дать разные экземпляры.

**58. Singleton автоматически thread-safe?** Нет. Он может обслуживать множество запросов одновременно; mutable request state в общих полях опасен.

**59. Prototype внутри singleton обновляется на каждом вызове?** При обычном constructor injection он разрешается один раз. Для нового получения нужен provider/lookup или соответствующий proxy.

**60. Что такое scoped proxy?** Посредник, который разрешает текущий target согласно scope, например request, при использовании из более долгоживущего бина.

**61. BeanFactoryPostProcessor и BeanPostProcessor?** Первый работает с определениями, второй - с экземплярами в lifecycle. Изменять рецепт и оборачивать готовый объект - разные задачи.

**62. Когда вызывается PostConstruct?** После injection на стадии инициализации управляемого объекта. Это не гарантия, что внутренний вызов transactional-метода уже проходит через финальный AOP proxy.

**63. Почему цикл конструкторов - проблема?** Для создания A нужен B, а для B уже нужен A. Обычно это повод изменить ответственность, а не скрывать цикл полевым injection.

**64. @Bean отличается от @Component?** Bean описывает создание результата фабричного метода; Component делает класс кандидатом сканирования. Bean удобен для сторонних классов и явной сборки.

**65. Что меняет proxyBeanMethods=false?** Отключает enhancement межметодных Bean-вызовов конфигурации. Прямой вызов Java-метода не обязан вернуть уже существующий контейнерный singleton.

**66. Что входит в SpringBootApplication?** Boot configuration, component scan и auto-configuration. Она не является сокращением «включить вообще все Spring-проекты».

**67. Starter и auto-configuration - одно?** Starter подключает набор зависимостей. Auto-configuration создаёт настройки/бины по условиям; наличие jar не означает, что все условия выполнены.

**68. Почему Boot не создал ожидаемый бин?** Проверьте classpath, scan, profile, property conditions, существующие кандидаты и condition report. Возможна ошибка конфигурации, а не «магия Boot сломалась».

**69. Почему core entity не нашлась?** Component scan и EntityScan различаются; пакет core может лежать вне корня BackendMain. В проекте entity packages заданы явно.

**70. @Value или ConfigurationProperties?** Для одного значения удобен Value, для связанной типизированной группы - ConfigurationProperties с validation. Секретность не обеспечивается выбором любой из них.

**71. Зачем profiles?** Для переключения наборов бинов/настроек по окружению. Profile не хранит секрет безопасно и не доказывает готовность окружения.

**72. Что делает AOP proxy?** Перехватывает подходящий вызов и добавляет advice вокруг target method. Не переписывает автоматически все прямые обращения к this/полям.

**73. Почему @Transactional на private методе обычно не решает задачу?** Обычный Spring proxy не перехватывает private self-call как отдельный публичный контракт. Нужна подходящая внешняя граница или программная транзакция.

**74. Можно ли new Service с аннотацией и получить транзакцию?** Не в обычной контейнерной proxy-модели. Получить нужно управляемый бин либо явно использовать нужную инфраструктуру.

**75. Что делает DispatcherServlet?** Центрально координирует mapping, handler invocation, преобразование аргументов/результатов и обработку ошибок. Бизнес-операции выполняют вызываемые компоненты.

**76. Filter, interceptor и aspect - где различие?** Filter оборачивает servlet processing, interceptor - MVC handler, aspect - вызов метода бина. Порядок и область ошибок у них различны.

**77. RequestParam и RequestBody?** Первый получает query/form parameter по правилам binding, второй читает тело через message converter. JSON-поле не становится RequestParam автоматически.

**78. RestController и Controller?** RestController добавляет response-body semantics к Controller. Обычный Controller может выбирать view и тоже может иметь ResponseBody на отдельных методах.

**79. Что даёт ResponseEntity?** Управление статусом, заголовками и телом. Например, 201 и Location созданного заказа.

**80. Почему GET не должен создавать заказ?** Его safe-семантика позволяет кеширование, предварительное чтение и повторы без ожидания бизнес-изменений. Создание лучше выражать соответствующей командой.

**81. DELETE всегда обязан вернуть один и тот же status?** Нет. Идемпотентность относится к ожидаемому эффекту повторов, а не к буквальному равенству ответов.

**82. PATCH всегда идемпотентен?** Нет: «установить quantity=5» и «увеличить на 1» имеют разные свойства. Контракт частичной операции должен быть определён явно.

**83. Зачем DTO, если есть entity?** Чтобы ограничить данные API, отделить схему БД и избежать случайных lazy loads/циклов/утечки полей. DTO не отменяет проверку прав.

**84. Что реально запускает Bean Validation?** Инфраструктура MVC/method validation/явный Validator. Одной аннотации constraint в произвольном объекте недостаточно.

**85. NotNull и NotBlank?** NotNull требует присутствие значения, NotBlank - непробельную строку. Пустая строка проходит NotNull.

**86. Positive гарантирует обязательное BigDecimal-поле?** Обычно null допустим для самого Positive; обязательность задаётся NotNull. Для primitive null невозможен, но default 0 может не пройти Positive.

**87. Как вернуть единый формат ошибок?** Настроить ControllerAdvice/ExceptionHandler и безопасную error model. Ошибки filters/security должны быть согласованы отдельным entry point/handler.

**88. Authentication и authorization?** Первая устанавливает субъекта, вторая разрешает действие. Успешный login не означает право изменить любой заказ.

**89. HasRole('ADMIN') проверяет строку ADMIN?** При типичной политике проверяется ROLE_ADMIN. Пользовательские преобразования authorities и префиксы следует учитывать отдельно.

**90. Несколько SecurityFilterChain применяются все?** Выбирается первая подходящая цепочка по configured order/matcher. Её внутренние request rules - отдельный шаг.

**91. JWT скрывает содержимое от пользователя?** Подписанный JWT обычно не шифрует payload. Любой держатель может прочитать claims; подпись защищает целостность и доверие к издателю.

**92. Достаточно проверить подпись JWT?** Нет: нужны algorithm policy, срок и другие claims, issuer/audience и прикладные правила. В проекте ещё проверяется sid/аккаунт в БД.

**93. Чем access отличается от refresh?** Access предъявляют API, refresh используют для обновления доступа по отдельной политике. В проекте refresh - случайный ротируемый секрет с hash в БД.

**94. Почему пароль нельзя хешировать обычным SHA-256?** Человеческие пароли имеют низкую энтропию и быстро перебираются. Нужен адаптивный password hashing с salt и стоимостью вычисления.

**95. STATELESS означает отсутствие БД-сессий?** Нет. Это политика HTTP session в Security; приложение может хранить refresh session и выполнять server-side проверки access JWT.

**96. CORS защищает API от неавторизованного curl?** Нет, CORS - ограничение браузерного cross-origin доступа. Серверные authorization rules обязательны независимо от браузера.

**97. При JWT можно всегда отключить CSRF?** Нет. Решение зависит от способа автоматической отправки credentials, в частности cookie. Само слово JWT или stateless не является доказательством.

**98. Async наследует транзакцию вызывающего потока?** Обычная thread-bound транзакция автоматически не переносится. Асинхронный код должен иметь собственную корректную границу и не делить небезопасную Session.

**99. Cacheable хранит результат навсегда?** TTL/eviction/распределённость задаются provider/configuration. Аннотация управляет обращением к абстракции кэша и ключом.

**100. Actuator health UP означает, что все функции исправны?** Нет. Он отражает настроенные indicators в данный момент. Авторизация, бизнес-инварианты и миграции требуют своих проверок.

# 35. Вопросы 101-150: JDBC, JPA и транзакции

**101. Где находится JDBC в Spring Data JPA?** ORM формирует SQL и использует JDBC-драйвер для обычного реляционного доступа. Spring Data не устраняет JDBC, а скрывает часть работы более высоким API.

**102. Зачем DataSource вместо открытия нового DriverManager connection каждый раз?** Он отделяет получение соединения от клиента и позволяет pooling/configuration. Сам интерфейс DataSource не означает автоматически наличие пула.

**103. Что делает close у pooled connection?** Обычно возвращает логическое соединение в пул. Это не обязательно физическое закрытие TCP-соединения с PostgreSQL.

**104. Чем PreparedStatement защищает от injection?** Связывает значения отдельно от SQL-кода. Если пользовательский ввод всё равно склеили в SQL, создание PreparedStatement после конкатенации проблему не исправит.

**105. Можно ли передать имя сортируемой колонки через ?** Нет, placeholder предназначен для значения. Идентификатор и направление выбирают из разрешённого набора и строят контролируемую часть запроса.

**106. ExecuteQuery, executeUpdate и execute?** Query получает ResultSet, update - число затронутых строк в обычном DML, execute обслуживает общий случай с разными видами результатов.

**107. Почему перед чтением ResultSet нужен next?** Курсор начинается до первой строки. Next переходит к строке и сообщает её наличие; индексы параметров/колонок начинаются с 1.

**108. Что вернёт getInt для SQL NULL?** Примитивное значение 0 с необходимостью проверить wasNull; альтернативно используют подходящий nullable getObject. Иначе null и настоящий ноль будут спутаны.

**109. Что такое auto-commit?** Режим самостоятельного завершения отдельных statements по правилам JDBC. Для атомарного сценария из нескольких действий нужна общая явная транзакция.

**110. Batch гарантирует «всё или ничего»?** Не сам по себе. Гарантия зависит от транзакции, драйвера и обработки ошибок; отдельные результаты batch могут различаться.

**111. Что такое SQLState?** Стандартизированная категория/код ошибки JDBC. Помогает отличать constraint conflict, неправильные данные и проблемы ресурса вместе с vendor-specific сведениями.

**112. Зачем JdbcTemplate, если JDBC уже есть?** Он управляет повторяющимся кодом ресурсов и exception translation, оставляя SQL и mapping результата. Это не полноценный ORM и не автоматическое решение любой транзакции.

**113. Чем JPA отличается от Hibernate?** JPA - спецификация API/поведения, Hibernate - провайдер с расширениями. SoftDelete относится к Hibernate, а Entity - к Jakarta Persistence.

**114. Что такое persistence context?** Набор управляемых сущностей и инфраструктура отслеживания их состояния в единице работы. Он поддерживает identity map и dirty checking, а не является общей БД в памяти.

**115. Можно ли делить EntityManager между потоками?** Конкретную единицу работы обычно нельзя. Фабрика thread-safe, а внедрённая Spring proxy-ссылка может делегировать разным текущим контекстам.

**116. New, managed, detached и removed?** Новый объект ещё не управляется; managed отслеживается; detached уже вне контекста; removed помечен к удалению. Наличие id не описывает все состояния однозначно.

**117. Persist и merge?** Persist предназначен для присоединения новой entity по контракту; merge копирует состояние в managed entity и возвращает её. Исходный merge-аргумент не обязательно становится managed.

**118. Почему нужно учитывать результат save?** Save может делегировать merge и вернуть другой managed-экземпляр. Последующие изменения старой detached-копии не обязаны сохраниться.

**119. Как Spring Data определяет новую entity?** Использует state detection, обычно nullable version, затем id, либо настроенный Persistable/другую стратегию. Ненулевой id не является универсальным ответом.

**120. Setter сохраняет изменения без save?** У managed entity в корректной write-транзакции dirty checking может сформировать UPDATE. Detached-объект и read-only режим меняют ситуацию; важен lifecycle.

**121. Flush равен commit?** Нет. Flush отправляет изменения в текущую DB-транзакцию, commit завершает её. После flush ещё возможен rollback.

**122. Почему constraint error возник после возврата метода?** SQL мог быть отложен до flush/commit, который выполняет interceptor после target-body. Пустой catch вокруг setter этого не перехватит.

**123. Первый уровень кэша исключает любой повторный SELECT?** Нет. Он гарантирует управляемую идентичность в контексте, но запросы и выборки по условиям могут всё равно выполняться.

**124. Что делает clear?** Отсоединяет сущности из context. Незасинхронизированные изменения могут потеряться, поэтому перед clear оценивают необходимость flush.

**125. Почему возникает LazyInitializationException?** Для неинициализированной связи нужен уже недоступный persistence context. Нужные данные загружают и преобразуют в DTO внутри сценария.

**126. EAGER гарантирует JOIN?** Нет. Провайдер может использовать дополнительные SELECT. EAGER определяет требование загрузки, а не точный SQL и не отсутствие N+1.

**127. Что такое N+1?** Один запрос за набором и по дополнительному запросу на каждый элемент/связь. Решение выбирают по SQL: fetch, graph, batch, projection, агрегация.

**128. Что означает mappedBy?** Имя Java-свойства owning relationship на другой стороне. Это не SQL-имя FK и не указание автоматически синхронизировать обе коллекции.

**129. Зачем обновлять обе стороны bidirectional relationship?** Чтобы граф Java-объектов был согласован в памяти. БД-связь сохраняется по owning side, но обратная коллекция сама не обязана обновиться.

**130. Cascade REMOVE и ON DELETE CASCADE одинаковы?** Нет. Первый распространяет ORM-операции, второй выполняется БД при физическом удалении. Soft delete и bulk SQL могут иметь другую семантику.

**131. OrphanRemoval - это CascadeType.ALL?** Нет. Он задаёт удаление осиротевшего дочернего объекта при разрыве принадлежащей связи. Cascade определяет распространение конкретных persistence-операций.

**132. Почему ORDINAL enum рискован?** Перестановка констант меняет интерпретацию числа в существующих данных. STRING устойчив к порядку, но переименование тоже требует миграции.

**133. JPQL и SQL?** JPQL использует модель сущностей и их полей, SQL - физическую схему. HQL может добавлять возможности Hibernate сверх стандартного JPQL.

**134. Что даёт Modifying?** Обозначает query method как изменяющий запрос. Он требует подходящей транзакции и не превращает bulk UPDATE в поштучный entity lifecycle.

**135. Зачем clear после bulk UPDATE?** Managed-объекты могут хранить старые значения, потому что SQL изменил БД в обход dirty checking. Порядок flush/clear должен сохранять локальные изменения.

**136. Почему fetch коллекции со страницей опасен?** Join умножает строки, а limit по строкам не равен limit по родителям. Возможны in-memory pagination, предупреждения или запрет; часто нужны два этапа.

**137. Page и Slice?** Page сообщает общий размер и часто требует COUNT. Slice обычно отвечает, есть ли следующая порция, без обязательного полного подсчёта.

**138. Specification отменяет необходимость знать SQL?** Нет. Она строит критерии, но joins, duplicates, count, indexes и стоимость остаются реальными свойствами запроса.

**139. ReadOnly запрещает любую запись?** Не универсально. Это режим/подсказка с реализационно зависимой оптимизацией и иногда enforcement; нельзя использовать как основной контроль прав.

**140. Rollback происходит при любом Exception?** Типичный default - RuntimeException/Error, а checked зависит от rollback rules и общей настройки. Нужно назвать фактическую политику.

**141. REQUIRED и REQUIRES_NEW?** REQUIRED разделяет существующую физическую транзакцию, REQUIRES_NEW открывает независимую с приостановкой внешней. Последняя может потребовать дополнительное соединение.

**142. MANDATORY зачем?** Чтобы запретить выполнение операции без уже активной транзакции. В проекте это защищает смысл методов write-lock и согласованного аудита.

**143. Catch внутреннего exception гарантирует commit?** Нет. Общая транзакция может уже быть rollback-only. Внешний commit тогда может завершиться UnexpectedRollbackException.

**144. NESTED равен новой транзакции?** Обычно это savepoint внутри физической транзакции при поддержке менеджера. REQUIRES_NEW имеет независимую физическую границу.

**145. Что защищает Version?** Обнаруживает конфликт изменения конкретной версионируемой строки. Не автоматически защищает сумму нескольких независимых строк или весь бизнес-агрегат.

**146. Pessimistic lock нужен до проверки или после?** Для read-modify-write общий lock берут до окончательной проверки состояния и держат до завершения записи. Проверка до lock могла устареть.

**147. Serializable означает, что ошибок конкурентности не будет?** Нет. СУБД может отклонить конфликтующую транзакцию для сохранения serializable-эффекта. Нужен ограниченный корректный retry всего сценария.

**148. Почему synchronized не заменяет DB lock?** Он координирует потоки одного процесса по одному монитору. Другой backend или клиент БД не обязан использовать этот монитор.

**149. Flyway и ddl-auto=validate дублируют друг друга?** Нет. Flyway изменяет схему управляемыми миграциями, validate проверяет соответствие ORM-mapping готовой структуре.

**150. Soft delete автоматически фильтрует JdbcTemplate?** Нет. Прямой SQL сам задаёт условия active/archived. ORM-правило не переписывает произвольные JDBC statements.

# 36. Вопросы 151-200: ваша система

**151. Почему проект разделён на несколько модулей?** Для повторного использования модели/правил и независимых интерфейсов. Цена - необходимость поддерживать согласованные инфраструктурные адаптеры и сборку.

**152. Можно ли запустить core без Spring?** Да, сервисы собираются вручную с подходящими repository и Transactions. При этом core всё ещё использует JPA/Hibernate в модели и инфраструктуре.

**153. Где в проекте DI без Autowired?** Конструкторы core-сервисов принимают зависимости, а ServicesConfig передаёт их через Bean-method parameters. DI - не синоним аннотации Autowired.

**154. Почему SpringProductsRepository одновременно наследует несколько интерфейсов?** Он предоставляет контракт core и подключает CRUD/Specification инфраструктуру Spring Data. Proxy реализует общий repository API для сервисов.

**155. Почему это не JpaRepository напрямую?** Фактический интерфейс расширяет ListCrudRepository и JpaSpecificationExecutor. Набор доступных методов следует определять по реальному наследованию.

**156. Для чего Transactions?** Он отделяет бизнес-сценарий от конкретного способа управления транзакцией: HibernateTransactions в одном окружении, TransactionTemplate в backend.

**157. Как вложенные core-вызовы получают общую Hibernate Session?** HibernateTransactions хранит активную Session по factory в ThreadLocal и повторно использует её, очищая storage по завершении. Это не механизм передачи Session другому потоку.

**158. Как backend связывает core Transactions со Spring?** Bean создаёт TransactionTemplate на PlatformTransactionManager и выполняет callback через него. Обычная propagation template присоединяется к подходящей существующей транзакции.

**159. Почему entity scan задан явно?** Пакет core entities находится вне backend-поддерева. EntityScan включает оба набора, не превращая core services в компоненты сканирования.

**160. Почему Product.price - BigDecimal?** Для точной десятичной арифметики и NUMERIC mapping. Precision/scale и правила округления должны быть согласованы с входной валидацией и SQL.

**161. Зачем purchasePrice у OrderItem?** Фиксирует цену позиции на момент операции и сохраняет историческую сумму. Текущая цена каталога может впоследствии измениться.

**162. Почему Inventory имеет уникальную пару product/warehouse?** В выбранной модели на одном складе один остаток данного товара. Без UNIQUE несколько строк могли бы неоднозначно представлять одно состояние.

**163. Отрицательный остаток допустим?** Нет: core и V18 требуют quantity >= 0. Резерв считается отдельно и не должен превышать физическую доступность.

**164. Что резервирует склад?** Позиции заказов в CREATED и APPROVED. Доступность рассчитывается как физическая сумма минус активные резервы.

**165. Когда товар физически списывается?** При переходе заказа в DELIVERED через OrderStock.deliver. Один только CREATED резервирует логически и не уменьшает физический остаток.

**166. Что если менеджер повторит DELIVERED?** ChangeStatus возвращается при совпадении текущего и нового статуса. Это предотвращает второе списание на этом пути; всё равно важна блокировка и общая транзакция.

**167. Можно ли вернуть доставленный заказ в CREATED?** TransitionStock запрещает смену статуса уже доставленного заказа. Возврат товара потребовал бы отдельного бизнес-сценария, а не обхода проверки.

**168. Есть ли строгая таблица всех остальных переходов?** В просмотренном transitionStock нет полной матрицы всех разрешённых пар. Нельзя рассказывать о state machine, которой код фактически не задаёт.

**169. Почему товар блокируют, а не только запись Inventory?** Один товар объединяет несколько складов и резервов. Общий product lock служит точкой координации всего расчёта при соблюдении протокола всеми writers.

**170. Зачем сортировать product ids перед lock?** Единый порядок уменьшает риск взаимной блокировки при заказах с несколькими товарами. Это не абсолютное доказательство отсутствия deadlock во всей системе.

**171. Почему после lock пересчитывают доступность?** Предыдущее чтение могло устареть, пока поток ожидал. Окончательная проверка должна видеть состояние после завершения предыдущего владельца lock.

**172. Как редактируемый заказ учитывается в резерве?** Его прежние позиции исключаются из общего занятого количества, затем проверяется новый полный набор. Иначе собственный резерв учитывался бы дважды.

**173. Почему одинаковые товары в списке нормализуются?** Суммирование повторных productId позволяет проверить общий запрос по товару и лимиты количества. Несколько отдельных строк не должны обходить ограничение доступности.

**174. Зачем количества суммируются в long?** Чтобы уменьшить риск переполнения int при агрегации нескольких позиций/остатков. Перед возвращением к int проверяется допустимый бизнес-предел.

**175. Может ли UI гарантировать наличие товара?** Нет, показанное значение устаревает при конкуренции. Серверная повторная проверка внутри транзакции обязательна для согласованной записи.

**176. Зачем у entity Version вместе с write locks?** Version обнаруживает определённые stale updates, lock сериализует критический сценарий. Они защищают разные ситуации и не заменяют полный протокол записи.

**177. Что происходит при удалении заказа?** Core явно обходит и удаляет позиции и историю, затем заказ; Hibernate soft delete сохраняет строки с отметкой. Это не автоматическое физическое FK-cascade.

**178. Освобождает ли удаление доставленного заказа физический товар?** В рассматриваемом deleteOrder нет отдельного возврата списанных остатков. Не следует обещать возврат товара без реализованного сценария.

**179. В чём разница AuditLog и AuditEvent?** Первый описывает историю статусов заказа, второй - общий структурированный аудит действий/объектов. Диагностический log - ещё один отдельный механизм.

**180. Почему аудит пишет JDBC из ORM listener?** Чтобы участвовать в текущем соединении и не добавлять новые JPA actions в flush callback с риском рекурсии. Конфигурация общего DataSource/manager важна.

**181. Почему login failure имеет REQUIRES_NEW?** Неуспешный вход нужно зафиксировать независимо от успеха основной операции. Это сознательный выбор границы аудита, а не правило для всех записей.

**182. Что делает correlation id?** Связывает error response, request и записи журнала. Он помогает диагностике, но не является credential или доказательством полномочий.

**183. Почему JWT проверяется через БД?** Так немедленно учитываются отзыв sid, enabled и политика смены пароля. Цена - DB-запросы и зависимость от доступности хранилища сессий.

**184. Что произойдёт, если роль изменилась после выдачи access JWT?** Converter строит authority из текущего пользователя/учётных данных в БД. Не следует считать старый roles claim единственным источником прав в этой реализации.

**185. Почему refresh хранится как hash?** Случайный секрет предъявляется клиентом, сервер сравнивает его идентификатор-хеш и отслеживает использование. Утечка БД не должна сразу выдавать готовые plaintext refresh credentials.

**186. Зачем noRollbackFor при replay refresh?** Сессия отзывается, затем метод бросает InvalidRefreshSessionException. Без корректного правила rollback этот отзыв мог бы отмениться вместе с ошибкой.

**187. Почему BCrypt и SHA-256 используются в разных местах?** Bcrypt замедляет подбор человеческих паролей. SHA-256 идентифицирует уже высокоэнтропийный случайный refresh-токен; исходная модель угроз отличается.

**188. Какие маршруты публичны?** В SecurityConfig публичная chain включает login/refresh/logout, Swagger/OpenAPI и health. Это не означает, что некорректный refresh будет успешно обработан бизнес-сервисом.

**189. Почему permitAll logout не означает возможность отозвать любую сессию по id?** Операция использует предъявленный refresh-секрет по контракту. Разрешение пройти security chain не отменяет проверку самого секрета внутри сценария.

**190. Все USER видят только свои заказы?** Этого нельзя утверждать по общим REST handlers. Новые checkout/contents используют субъект JWT и сценарии владельца, но объектные права всё равно нужно определять отдельно для каждого endpoint.

**191. Может ли null notes в PATCH очистить примечание?** В текущем OrdersController null означает сохранение старого значения. Для явной очистки нужен другой контракт различения absent/null/value.

**192. Совпадают ли правила нулевой цены на всех уровнях?** Нет: CreateProductRequest требует Positive, core и миграция допускают неотрицательную цену. Это известная разница контрактов, требующая бизнес-решения.

**193. Зачем SearchPaging добавляет уникальный sort?** Чтобы записи с равным основным полем имели определённый порядок. Это не фиксирует весь набор данных при конкурентных вставках между запросами страниц.

**194. Почему size ограничен сотней?** Ограничение контролирует стоимость ответа и нагрузку. Оно не устраняет дорогой COUNT, плохие joins или тяжёлую сортировку без индекса.

**195. Почему JdbcStatisticsRepository считает в SQL?** БД агрегирует нужные данные без загрузки всех entities. Прямой SQL должен явно учитывать soft delete и смысл active/archived связей.

**196. Почему в production validate, а в части тестов create-drop?** Production-схема управляется миграциями; тестовая H2 создаётся из mapping для изолированных проверок. Это разные цели и разные пределы доказательства.

**197. H2-тесты доказывают правильность PostgreSQL migrations?** Не автоматически, особенно при Flyway disabled. Требуется отдельный запуск миграций и сценариев на PostgreSQL.

**198. Где искать фактические версии?** Java toolchain - root build, Gradle - wrapper properties, библиотеки - version catalog и resolved dependency graph. README может отставать от конфигурации.

**199. Наличие Android в README доказывает готовое приложение?** Нет. Демонстрировать следует файлы и работающий результат текущего checkout; roadmap и реализованный модуль нужно различать.

**200. Какие улучшения назвать без преувеличения?** Согласовать DTO/core constraints, определить объектные права, расширить PostgreSQL-проверки конкурентности/миграций, убрать тяжёлые getAll-фильтры и вынести HTTP orchestration в facade. Приоритет зависит от требований.

# 37. Практические задачи и разбор ловушек

## Задача 1. Почему изменение не сохранилось?

```java
Product p = readInPreviousTransaction(id);
p.setName("New name");
// Текущий код не открывает транзакцию и не делает merge.
```

**Разбор:** после завершения предыдущего context объект может быть detached. Setter меняет только Java-состояние. Загрузите managed entity внутри write-сценария и примените разрешённую правку либо осознанно используйте результат merge. Дополнительный вопрос: нельзя ли затереть этим устаревшим объектом другие поля?

## Задача 2. Почему внутренняя REQUIRES_NEW не сработала?

```java
@Service
class Importer {
    @Transactional
    public void run() { saveRow(); }
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveRow() { /* insert */ }
}
```

**Разбор:** self-call не проходит через обычный proxy заново. SaveRow выполнится в транзакции run, если run был корректно вызван через бин, но новая независимая транзакция не появится из одной аннотации. Выделите отдельный writer-bean или программную границу; сначала решите, нужна атомарность файла или независимость строк.

## Задача 3. Почему merge вернул другой объект?

```java
Product detached = earlier;
Product saved = repository.save(detached);
detached.setName("Changed again");
```

**Разбор:** save может использовать merge. Управляемой становится возвращённая копия, а не исходный аргумент. Проверяйте состояние и transaction boundary, используйте saved, а для PATCH лучше изменять заново загруженную managed entity с выбранными полями.

## Задача 4. Два заказа по 7 при остатке 10

**Условие:** оба клиента сначала прочитали «10 доступно», затем вставили разные позиции. Version каждой новой позиции не конфликтует.

**Разбор:** нужен общий механизм защиты агрегатного инварианта. В проекте это блокировка товара и окончательный пересчёт внутри общей транзакции. Альтернативы - условный атомарный резерв в отдельной строке или serializable с корректным retry. Одна проверка размера/количества DTO гонку не исправляет.

## Задача 5. Почему rollback не отменил сообщение?

```java
@Transactional
public void approve() {
    updateOrder();
    externalMailer.send("Approved");
    throw new IllegalStateException("failure");
}
```

**Разбор:** локальная транзакция БД не откатывает уже выполненную отправку. Даже after-commit listener оставляет окно потери сообщения при падении. Для требуемой надёжности применяют outbox и идемпотентную доставку либо иной согласованный протокол.

## Задача 6. Где появится N+1?

```java
List<Order> orders = repository.findAll();
return orders.stream()
    .map(o -> new OrderRow(o.getId(), o.getUser().getUsername()))
    .toList();
```

**Разбор:** зависит от mapping и fetch plan. Если users догружаются отдельно, будет дополнительный SQL на связанные записи; EAGER тоже может использовать secondary selects. Докажите логом SQL/счётчиком, затем сравните fetch join/graph/projection. При закрытом context возможна lazy error вместо дополнительных запросов.

## Задача 7. Почему пропали заказы без позиций?

```sql
SELECT o.id
FROM orders o
LEFT JOIN order_items i ON i.order_id = o.id
WHERE i.deleted_at IS NULL AND i.quantity > 0;
```

**Разбор:** для строки без item quantity=NULL, а сравнение > 0 не true. Фильтр по правой таблице в WHERE исключил такую строку. Если нужно сохранить заказы без подходящих позиций, перенесите условие связи в ON и определите смысл soft delete для обеих таблиц.

## Задача 8. Почему тест уникальности «зелёный»?

**Условие:** тест вызвал save двух объектов с одинаковым sku, не сделал flush, затем тестовая транзакция откатилась.

**Разбор:** реальный INSERT/constraint check мог не произойти до rollback. Проверьте flush и границу commit, корректность схемы БД и ожидаемый тип ошибки. Проверка mock-вызова repository не доказывает UNIQUE в production.

## Задача 9. Почему отзыв сессии исчез после ошибки?

**Условие:** refresh replay пометил session revoked, затем бросил runtime exception; транзакция откатилась.

**Разбор:** ошибка для клиента и сохранение security-факта требуют специально выбранной границы. В проекте используется noRollbackFor для конкретного исключения. Не распространяйте это правило на все ошибки: можно случайно коммитить частично выполненный сценарий.

## Задача 10. Можно ли проверить роль и считать задачу решённой?

**Условие:** USER A вызывает PATCH заказа USER B по известному UUID. Общая chain разрешает USER, метод меняет только notes.

**Разбор:** роль не определяет право на конкретный объект. Требование владения нужно выразить в сервисе/запросе/authorization policy и проверить тестом «свой/чужой». UUID затрудняет угадывание, но не является authorization mechanism.

## Задача 11. Почему число запросов выросло после добавления поля DTO?

**Разбор:** mapping нового поля мог обратиться к lazy-связи либо вызвать mapper с дополнительным repository lookup для каждой строки. DTO не гарантирует отсутствие N+1: значение имеет путь его построения. Профилируйте endpoint целиком с realistic dataset и открытой/закрытой транзакционной границей.

## Задача 12. Что спросить перед добавлением retry?

Выясните, является ли ошибка временной, мог ли предыдущий запрос завершиться, какие side effects повторятся, есть ли idempotency key, сколько попыток разрешено и где расположен backoff. Retry вокруг одной последней SQL-команды не всегда повторяет весь необходимый инвариант. Избыточные повторы могут усиливать перегрузку.

## Алгоритм ответа на незнакомый фрагмент

- Определить, кто создаёт объект и проходит ли вызов через infrastructure/proxy.
- Найти границу context/transaction и состояние entity в каждой точке.
- Предсказать SQL, момент flush и место возможной ошибки.
- Рассмотреть два одновременных запроса и повтор после сетевого сбоя.
- Проверить, какие входные поля контролирует клиент и где проверяются права.
- Назвать наблюдение, которое подтвердит гипотезу: тест, SQL trace, lock graph, log или query plan.
