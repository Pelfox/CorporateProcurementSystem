# Система корпоративных закупок

Данный репозиторий содержит в себе проект на Java, реализующий базовую систему
создания и отслеживания корпоративных закупок. Проект поделён на 4 части:

- Консольное приложение,
- Desktop-приложение на JavaFX,
- Web-приложение с REST API,
- Мобильное приложение для Android.

## Требования для запуска

Проект построен на последней стабильной версии Java (LTS) - 25. Помимо этого,
используется система сборки Gradle последней версии. Для сборки единого
JAR-файла используется плагин [Shadow Gradle](https://gradleup.com/shadow/).

```bash
./gradlew shadowJar
```

## Backend: разработка и проверки

Backend запускается отдельным процессом на Java 25. Пока аутентификация не реализована,
все HTTP-операции закрыты Spring Security; стандартная учётная запись Spring Boot
не создаётся. Предметные HTTP-тесты проверяют существующую бизнес-логику без фильтров,
а `SecurityBoundaryTest` отдельно проверяет запрет внешнего доступа.

Конфигурация подключения берётся из `DB_URL`, `POSTGRES_USER`, `POSTGRES_PASSWORD`.
Пример без секретов — `.env.example`. Spring Boot сам не читает `.env`: передайте
значения через окружение PowerShell или настройки запуска IDE.

Для отдельной dev-БД с собственным томом и портом 5433, не затрагивающей прежний
`docker-compose.yml`, после задания переменных пользователя и пароля выполните:

```powershell
docker compose -f compose.auth-dev.yml up -d
.\gradlew.bat :cps-backend:bootRun
```

Начальная БД — `corporate_procurement_auth_dev`. Схемой управляет только Flyway;
Hibernate использует `validate`. Миграции V1/V2 сохранены, V3 добавляет credentials,
сессии и историю refresh-токенов. Повторный запуск применённые миграции не меняет.

Существующие пользователи при переходе с V2 сохраняют ID, заказы и ссылки, но
получают `enabled=false`, `must_change_password=true` и `password_hash=NULL`.
Вход запрещён до административной выдачи индивидуального временного пароля.
Nullable-хэш нужен только для учётных записей без подготовленных credentials:
constraint БД запрещает включить пользователя без хэша. Новое создание всегда
получает готовый BCrypt-хэш. Ужесточать колонку до NOT NULL можно отдельной
миграцией только после подготовки credentials для всех сохранённых пользователей.

Для схемы без Flyway не включайте `baseline-on-migrate`: выберите новую пустую dev-БД
либо отдельно сравните схему с V1/V2 и только затем выполните управляемый baseline
на проверенную версию. Наличие таблицы `users` само по себе не доказывает соответствие.
Общий пароль миграцией не назначается.

Legacy `DataInitializer` больше не создаёт пользователей с общим хэшем и далёким
сроком действия. Для наполнения ему нужны индивидуальные подготовленные
`InitialCredentials`; прежний вызов без них пропускает наполнение пустой БД.
Это ограничение касается старых клиентов; их интерфейсы сейчас не перерабатываются.

Проверки из корня проекта:

```powershell
.\gradlew.bat :cps-core:test :cps-backend:test
# Задайте POSTGRES_TEST_URL, POSTGRES_TEST_USER, POSTGRES_TEST_PASSWORD
# для отдельной PostgreSQL test-БД, затем:
.\gradlew.bat :cps-backend:postgresTest
```

`test` проверяет core и HTTP-регрессию на H2. Отдельный `postgresTest` проверяет
реальные Flyway-миграции, обновление старых пользователей, JPA-связи, уникальность
хэша и общий откат транзакций. Без `POSTGRES_TEST_URL` задача завершается с ошибкой,
а не пропускает проверку незаметно. Поддерживается локальный PostgreSQL или контейнер.

Начальные параметры: `BCRYPT_STRENGTH=12`, `TEMPORARY_PASSWORD_TTL=PT24H`.
Ключи подписи, access/refresh и защищённые сценарии входа добавляются следующими блоками.
